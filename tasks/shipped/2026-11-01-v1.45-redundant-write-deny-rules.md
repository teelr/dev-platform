# v1.45 Redundant Write Deny Rules

v1.45 Redundant Write Deny Rules (2026-11-01, `tasks/redundant-write-deny-rules-spec.md`):
follow-up to v1.39, which added the rules, and to the v1.44 probe session, which surfaced the
startup warning.

## The verified problem

- Claude Code prints a warning at startup for each of `Write(//home/rich/.bashrc)`,
  `Write(//home/rich/.profile)` and `Write(//home/rich/.ssh/**)`: such a rule "is not matched by
  file permission checks — only Edit(path) rules are", and `Edit` rules cover all file-editing
  tools (seen in the output of a headless `claude -p` run).
- Each of the three paths already had an `Edit(...)` deny rule next to it in
  `settings/settings.json` (`grep -rn 'Write(' ...` found only these three `Write(` entries in
  tracked config, outside `tasks/shipped` and `projects/`). The `Write` lines protected nothing.
- A plain delete would not have reached the live file: `scripts/merge_settings.py` unions
  `permissions.deny` and its retract list only touched `permissions.allow`.

## What shipped

- `scripts/merge_settings.py`: the retract file may hold a `deny` list as well as `allow`
  (`{"allow": [...], "deny": [...]}`, each key optional). Same exact-string removal, applied
  to the matching list only; an entry in both a baseline list and the same retract list exits 2;
  a non-list value exits 2. A pre-v1.45 `allow`-only retract file behaves as before.
- `scripts/verify.sh`: the drift check counts leftovers on both lists.
- `settings/settings.json`: the three `Write(` deny entries are gone; the three `Edit(` entries
  stay. `settings/permissions-retract.json` gets a `deny` list with the same three strings.
- `tests/merge-settings` 13 → 17 checks, `tests/settings-baseline` 8 → 10 checks; gate fast
  549 → 555 PASS, 0 FAIL. Every new check was run against a mutated copy in the session
  scratchpad (Write rule re-added to the baseline, an `Edit` twin removed, a retract `deny`
  entry that is also in baseline `deny`, merge ignoring `deny`, the contradiction check dropped)
  and failed there; an unmutated copy had 0 failures.
- `settings/README.md`: the retract description covers `deny`, plus a bullet that a `Write(...)`
  permission rule is never matched.

## Findings

- A dry run of `merge_settings.py` against the real live file with the new retract list leaves
  the three `Edit(` deny entries and none of the `Write(` ones. The new verify count reads 3
  against the live file until the install runs.

## Scope honesty

- Not yet deployed. `./scripts/install.sh settings` changes the live permissions and is a
  post-merge step that needs the user's go-ahead.
- Tested after merge (2026-11-01): an `Edit(path)` deny blocks the `Write` tool. The `Write`
  tool, pointed at a new file `~/.ssh/claude-write-deny-probe.txt` (covered only by
  `Edit(//home/rich/.ssh/**)`, since the `Write` twin was gone), was refused with "File is in a
  directory that is denied by your permission settings." Only the `.ssh/**` rule was exercised;
  `.bashrc` and `.profile` use the same `Edit(...)` form but were not probed. The probe file's
  absence was not confirmed directly (a Bash `ls` of it was also denied).
- Checked after merge (2026-11-01): no project under `projects/` carries a `Write(` permission
  rule. A grep of every `.claude/settings.json` and `.claude/settings.local.json` found only
  `Bash(select:TodoWrite)` in `kermit-v3` and an rsync path containing `TIS-Writer-main` in
  `keystone_prototype`; neither is a `Write(` rule.
