# v1.31 Roadmap Path Input — a feature we shipped, documented, and made unreachable

v1.31 Roadmap Path Input, **closes v1.31** (2026-09-04, `tasks/roadmap-path-input-spec.md`): `ROADMAP_PATH` shipped in v1.13 so a project whose Roadmap Phase entries do not live at root `ROADMAP.md` could point the checks at the real file. Four scripts read it. **No consumer could reach it through CI** — the reusable workflow every consumer calls accepted exactly one input, `ref`.

**The documentation was the worse half.** `docs/CI-INTEGRATION.md` told consumers to set it "as an `env:` entry on the calling step/job in your `dev-platform-gate.yml`". That job is a reusable-workflow call — `uses:`, not `steps:` — and a job calling a reusable workflow accepts a restricted key set that excludes `env`. The instruction could not be followed by anyone who tried.

Keystone is the live cost. Its real roadmap is `docs/roadmap.md` (1063 lines). It maintains a **hand-written root `ROADMAP.md` index** of version headers plus a bespoke `CT-ROADMAP-INDEX` gate check to stop the two drifting, purely so our shared CI could parse anything. Its first attempt was a symlink, which produced false `COLLISION` failures against its own milestone history (`teelr/keystone#508` → `#509`). A consumer built, broke, and debugged a workaround for a feature we had already shipped and told them to use.

## The premise was verified before anything was built

The claim "a consumer cannot pass `ROADMAP_PATH` through the reusable workflow" was reasoned from GitHub's documented key set, not observed — so Change 1 was a scratch branch on live GitHub, run before a line of the fix. Two probe workflows, identical but for one key:

| Probe | Run `name` GitHub reported | Conclusion |
| ----- | -------------------------- | ---------- |
| A — `env:` on a `uses:` job | `.github/workflows/probe-a-env-on-uses.yml` (the **file path**) | `failure` |
| B — `with: roadmap_path:` on `@v1.30`, which lacks the input | `probe-b-unknown-input` (its declared `name:`) | `startup_failure` |

The contrast is the proof. Probe A's run could not resolve its own `name:` and fell back to the file path — GitHub rejected the file at workflow-validation time, at the `env:` key. Probe B parsed fine and failed later, at dispatch, on the unknown input. Both are real errors a consumer can hit, and both are now quoted in the docs. Scratch branch deleted; `gh api repos/teelr/dev-platform/branches` shows only `main`.

## What shipped

**`roadmap_path` input on `taxonomy-check.yml`, wired into both jobs.** Both `check_spec_taxonomy.sh` and `check_version_collision.py` receive it, so they cannot disagree about which document is the roadmap.

**The default is `ROADMAP.md`, never `''` — and that is the load-bearing decision.** The two reader families disagree about an empty value:

```console
$ ROADMAP_PATH= bash -c 'echo "${ROADMAP_PATH:-ROADMAP.md}"'
ROADMAP.md                  # bash :- treats empty as unset
$ ROADMAP_PATH= python3 -c "import os; print(repr(os.environ.get('ROADMAP_PATH','ROADMAP.md')))"
''                          # Python .get() treats empty as a VALUE
```

`Path(root) / ""` is the root **directory**. `.exists()` accepts it, so the "nothing to check" guard is skipped and `read_text()` raises:

```console
$ ROADMAP_PATH= python3 scripts/check_version_collision.py .
IsADirectoryError: [Errno 21] Is a directory: '.'
rc=1
```

Exit 1 is what the workflow renders as `::error::version collision detected`. An empty default would have handed a **false collision failure to every consumer who omitted the input** — a bug that fails on other people's repos, not ours. `scripts/lib/roadmap_path.py` now treats empty as unset for both Python readers as well, because the env var is still exported by hand for local runs where nothing validates it.

**`docs/CI-INTEGRATION.md` splits CI from local**, which the old text conflated: `with: roadmap_path:` in CI (requires `@v1.31`+), `export ROADMAP_PATH` locally. It states plainly that `env:` on the calling job does not work, so a reader who remembers the old advice learns why it changed instead of assuming the docs drifted. The symlink warning is kept verbatim.

**The consumer template** pins `@v1.31` and carries the input commented out — commented because the default is right for every consumer but keystone, and an active `with:` invites copy-pasting a path that does not exist in the copying repo. `fleet-install-template.sh` derives its `DEFAULT_PIN` from that line and now reports `Pin: @v1.31` with no separate edit.

## The file every consumer's CI calls had no test

Nothing in `tests/` asserted anything about `taxonomy-check.yml` — every hit was a fixture pin string — and `gate_fast.sh` validated JSON while never parsing a single YAML file. The highest-blast-radius file in the repo was the least checked.

`tests/reusable-workflow/` (7 assertions) now covers the input's declaration and default, per-job wiring, `GH_TOKEN` survival, the `job_workflow_ref` derivation, the cross-org `permissions` block, template/header pin agreement, and the empty-`ROADMAP_PATH` regression. **Written before the fix**: against the unmodified workflow it reported 4 PASS / 3 FAIL, failing exactly on the input, the wiring, and the crash — proving it detects the absence rather than describing the presence.

`gate_fast.sh` gained YAML validity, and both validity checks now fail on a zero-file glob instead of reporting `(0 files)` as a pass. The JSON check had that vacuity too; writing the guard for YAML made it obvious one line above.

## Three things found by checking rather than assuming

**The YAML check's first run failed on two scaffolding files** — `scaffolding/*/docker-compose.yml` carry `{{PROJECT_NAME}}` placeholders, and `{{` opens a flow mapping, so they are not parseable YAML until `new-project.sh` substitutes them. The spec had said to scan `scaffolding/`; that was wrong, and the check would have reported two failures against files that are correct as written. Scanning is now limited to `.github/workflows/` and `extensions/github-actions/`, with the reason recorded at the glob.

**One test assertion was itself the bug.** The `job_workflow_ref` check matched the bare string `workflow_sha` anywhere in the job — and the taxonomy step's own `run:` block contains a shell comment warning against `github.workflow_sha`. Comments inside a block scalar are part of the string, so the assertion flagged the warning as the regression. It now matches expression form (`${{ github.workflow_sha }}`) instead.

**PyYAML parses the `on:` key as boolean `True`.** YAML 1.1 semantics: `w['on']` raises `KeyError`, the trigger block is at `w[True]`. The spec's own acceptance-test snippet used `w['on']` and would have failed. Every assertion goes through a helper that tries both.

## Found, not fixed: a vacuous skip in `check_spec_taxonomy.sh`

While verifying the CI invocation shape end-to-end, the first probe reported rc=0 where it should have failed. Not a `ROADMAP_PATH` bug — the script exits 0 with "no tasks/ directory — skipping" **before the roadmap scan runs at all**. A repo with a `ROADMAP.md` but no `tasks/` directory has its Roadmap Phase headers silently unchecked, and the reusable workflow reports success.

Surveyed across the fleet: all seven consumers have a `tasks/` directory, so this is latent rather than live. Left unfixed — out of this phase's scope, and nobody is affected today. Recorded in `tasks/lessons/` so the next person to touch that script has it.

## Scope decisions

- **No auto-discovery.** Falling back to a candidate list when root `ROADMAP.md` is absent needs only a pin bump rather than a workflow edit, which is cheaper for consumers — and helps the motivating case not at all, because **keystone has a root `ROADMAP.md`**. Discovery would find the index file, stop, and change nothing.
- **No consumer repo touched.** Whether keystone retires its index and `CT-ROADMAP-INDEX` check is keystone's call, from its own session.
- **`check_spec_taxonomy.sh` and `check-phase-tags.sh` unchanged** — their `${VAR:-default}` reads were already correct.
