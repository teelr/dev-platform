`/merge` worktree-mode `--delete-branch` fix (2026-08-04, `tasks/merge-delete-branch-worktree-fix-spec.md`): `commands/merge.md` Step 4's `gh pr merge --squash --delete-branch` fails outright when run from inside a worktree — `main` is already checked out in the primary checkout, so `gh`'s local branch-delete half can't check anything out and the whole command aborts (confirmed live on kermit-v3 PR #236). The remote squash-merge already succeeded by that point, but the non-zero exit trips Step 4's "report verbatim and STOP" rule before Step 5's worktree teardown ever runs — leaving the remote branch and worktree both uncleaned, requiring a manual `gh api -X DELETE` afterward. Fix: Step 4's merge call is now conditional on `IN_WORKTREE` — branch mode unchanged (`--delete-branch` works fine there); worktree mode drops `--delete-branch` and deletes the remote branch explicitly via `gh api -X DELETE repos/${REPO}/git/refs/heads/${MERGED_BRANCH}` (touches no local checkout state), leaving local deletion to Step 5's existing, already-correct `git branch -D "${BR}"`. `/review` caught a real bug in the first cut: it used `${BR}` (the worktree's own current branch) as the delete target instead of the merged PR's actual head branch — wrong whenever `/merge <PR_NUM>` targets a PR other than the current branch's own (an explicitly documented, supported argument per Step 1), which would delete the wrong remote branch and skip cleanup of the right one. Fixed by deriving `MERGED_BRANCH` from `gh pr view "${PR_NUM}" --json headRefName` instead of assuming it equals `${BR}`. Small, scoped fix (~10-line diff) — no new Roadmap Phase, same class as PR #53/#54.
