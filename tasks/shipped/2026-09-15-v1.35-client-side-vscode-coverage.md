# v1.35 Client-Side VSCode Coverage — Windows client `settings.json`/`keybindings.json` tracking

v1.35 Client-Side VSCode Coverage (2026-09-15, `tasks/client-side-vscode-coverage-spec.md`): v0.6
(2026-05-11) tracked the VSCode Remote-SSH **server-side** extension list on neurX and explicitly
deferred client-side coverage — the laptop's `settings.json`/`keybindings.json`/snippets/theme —
to a future spec, because those files don't exist on the server and the client/server split needed
its own design pass. This is that follow-on, scoped down at `/plan` time to what the user actually
confirmed: the client machine is **Windows only**, dev-platform is already cloned there, and the
tracked scope is **`settings.json` + `keybindings.json` only** (no snippets, no client extension
list, no theme-only tracking).

## The central asymmetry, and how it shaped every Change

v0.6's `/code` session ran ON neurX, the target server, so its "capture the current state" Change
could just run `code --list-extensions` directly. This spec's `/code` session also runs on neurX,
but the target for THIS spec is a separate Windows machine the session has no access to — it
cannot read the real `settings.json`/`keybindings.json`, cannot run anything on the Windows box,
and cannot verify Windows-path detection against a real Windows environment. Every Change is
scoped to what's buildable and testable from neurX using **mocked** Windows tooling
(`cmd.exe`, `wslpath`, `cygpath`); the real first `capture` is a **manual post-merge step** the
user runs on the Windows machine, documented in the spec's "Post-Merge" section rather than faked
as a Change here.

## What shipped

- **`scripts/sync-vscode-client.sh`** — `resolve`/`capture`/`deploy`/`diff` modes. Detects the
  Windows VSCode `User/` directory via two branches: WSL (`$WSL_DISTRO_NAME` or `/proc/version`,
  bridging through `cmd.exe /c "echo %APPDATA%"` + `wslpath -u`) and Git-Bash/MSYS/Cygwin (`$APPDATA`
  inherited directly, `cygpath -u` if present, else a naive backslash-substitution fallback).
  `settings.json`/`keybindings.json` are treated as **opaque text** (`cp`/`diff -u`), never parsed
  as JSON — VSCode's own config format is JSONC (comments allowed) and hand-edited, unlike
  `server-extensions.json`, which dev-platform fully owns the shape of. Deploy is a straight copy,
  not a v1.6-style merge — nothing writes into these two files at runtime the way Claude Code
  writes grants into its own `settings.json`, and this targets one dedicated machine, not a fleet.
- **`scripts/install.sh vscode-client`** — new `install_vscode_client()` + case-statement entry,
  wired into `all`. Deliberately duplicates the Windows-detection logic inline rather than sourcing
  a shared helper or shelling out to the standalone script, matching two existing precedents already
  in this file: its own header keeps `REPO`-resolution inline for the same reason (`tests/worktree-default`
  copies `install.sh`/`verify.sh`/`uninstall.sh` alone, with no `scripts/lib/` alongside), and
  `install_vscode()` already duplicates `sync-vscode.sh`'s install loop rather than calling it.
  Permissive by design — "not a Windows client" (the common case on neurX itself) is a silent
  one-line skip, never an error.
- **`tests/vscode-client/`** — 18-assertion fixture suite (mocked `cmd.exe`/`wslpath`/`cygpath`),
  auto-discovered by `gate_fast.sh`. Gate grew 470 → 488 (`bash scripts/gate_fast.sh`, verified).

## Two real bugs the adversarial self-review pass caught (not in the spec's original test plan)

The spec's own 15 planned assertions all passed on the happy path, but re-reading the diff with
mocked *failure* injection (a `cmd.exe`/`wslpath` that exits non-zero, not just one that succeeds)
surfaced two defects in the verbatim spec code, fixed before merge:

1. **A failing `wslpath`/`cygpath` produced a false success.** `"$(wslpath -u "$x")/Code/User"`
   string-concatenates the command substitution's output with a literal suffix regardless of
   whether the substitution succeeded — an empty/failed translation silently resolved to the bare,
   plausible-looking path `/Code/User` instead of failing. Fixed by capturing the translation into
   a variable and only using it when non-empty.
2. **`install.sh`'s duplicated inline copy could silently kill the entire install run.** Both
   `sync-vscode-client.sh`'s call sites happen to invoke `resolve_vscode_user_dir()` as an `if`
   condition or the left side of `||` — both exempt from `set -e` — so a failing `cmd.exe` degraded
   gracefully there. `install.sh`'s copy has the identical bare assignment sitting in a plain `if`
   *body*, with no such exemption; under `set -e` a failing `cmd.exe` aborted `install.sh` entirely,
   silently skipping every category queued after `vscode-client` in `install.sh all` (`managed`,
   `git-hooks`, `worktree`, `shell`), with no error message at all. Confirmed both before and after
   the fix by injecting a failing mock into each script directly. Fixed with `|| true` on both
   command substitutions in both files, and 3 new regression assertions (Checks 16-18) added to
   `tests/vscode-client/run.sh` locking the fix in.

Neither bug was visible from the spec's happy-path mocks alone — both needed a mock that fails, not
just one that succeeds differently. Lessons: `tasks/lessons/2026-09-15-set-e-only-guards-conditionals-not-bare-assignments.md`.

## Scope decisions (per the spec)

- **No Mac/Linux client support** — the user confirmed the client machine is Windows only.
- **No snippets, client-side extension list, or theme-only tracking** — user-confirmed scope: settings + keybindings only.
- **`extensions/vscode/client-settings.json`/`client-keybindings.json` do NOT exist after this merge** — confirmed absent (not fabricated); populated by the user running `sync-vscode-client.sh capture` on the real Windows machine, per the spec's "Post-Merge" section.
- **Windows-path detection is unverified against a real Windows machine** — built and tested here against mocks only, flagged as such in the script's own header, `extensions/vscode/README.md`, and this record.

## Deviations from the spec (flagged at `/code` time, both minor)

- `tests/vscode-client/run.sh` Checks 13-15's `install.sh` invocations drop the spec's literal
  `HOME="$(mktemp -d)"` prefix: `install_vscode_client()` never reads `$HOME`, the prefix served no
  functional purpose, and it isn't needed to protect real state either way — the worktree guard
  refuses `HOME=` reassignment outright regardless of form (lesson:
  `2026-09-15-worktree-guard-refuses-any-home-reassignment.md`). Check 15 also needed a scratch,
  non-git-repo copy of `install.sh` (not a real git worktree) to control what its `REPO` resolves
  to, since `install.sh` always deploys from the main checkout, not the invoking worktree.
- `/home/rich/dev/CLAUDE.md`'s Install/Deploy category enumeration gained `vscode-client` — not in
  the spec's File Change Summary, added per the standing "Docs Ship With The Code" doc-sync duty
  since the same category list would otherwise go stale the same way `README.md`'s did before this
  spec.
