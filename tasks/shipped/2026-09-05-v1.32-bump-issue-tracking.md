# v1.32 Bump Issue Tracking — the row that nobody is working on

v1.32 Bump Issue Tracking, **closes v1.32** (2026-09-05, `tasks/bump-issue-tracking-spec.md`): `fleet-pins.sh` said a consumer was 19 minor versions behind. It did not say whether anyone was doing anything about it. Every active consumer had an open tracking issue that day — `teelr/keystone#515`, `teelr/kermit-v3#740`, `Osigin-LLC/SQRL#156`, `teelr/kermit-harness#391` — and not one appeared in the report. v1.31's own status check had to assemble that column by hand.

**The useful signal was the absence.** Showing `· issue #515 open` on tracked rows is the obvious half; the half that changes behaviour is marking a behind row with *nothing* — no bump PR, no tracking issue — as `untracked`. That is the row nobody will act on, and it was indistinguishable from a row with a merge-ready PR waiting.

## What shipped

**One call replaced two.** `fetch_open_bump` listed `/pulls`; `fetch_bump_refs` lists `/issues`, which returns pull requests as well, with `.pull_request` non-null on them. Verified on two repos before designing around it — one would have been weak evidence:

```console
keystone        /pulls → 1     PRs seen via /issues → 1
kermit-harness  /pulls → 3     PRs seen via /issues → 3
```

So the fleet sweep makes seven fewer HTTP round-trips than before, not seven more.

**The `.pull_request` split is load-bearing, and its failure case was already live.** Of the 7 items `/issues` returns for keystone, exactly one is a PR — and it is `PR #512`, the Dependabot bump, whose title matches the bump regex. Without the split, one object would be reported twice on one row: `PR #512` and `issue #512`. The suite's `current-1` fixture is that exact shape.

**`untracked` is gated four ways**, each ruling out a confident falsehood, and all four live in one predicate (`is_untracked`) used by both the row marker and its footnote — written twice in two shapes they would eventually disagree:

- `status == "behind"` — a frozen or up-to-date row needs no bump issue; marking it invites a pointless one.
- `bump_lookup == "ok"` — a failed, truncated, or never-run lookup has not established absence. Claiming it would send someone to file a duplicate of an issue that already exists.
- no open bump PR — a PR in flight *is* tracking.
- no tracking issue.

**No regex changed.** `BUMP_TITLE_RE` already matched every real bump-issue title and skipped every real near-miss — three open issues mention dev-platform without being bump asks (`Migrate tasks/lessons.md`, `Port gate-fast docs-only-diff`, `[dev-platform v1.22] Adopt gate_lock_acquire`). Checked before designing, so the phase deliberately touches neither regex.

`kermit-pa` came back as `— frozen (deployed, not developed) · issue #148 open`. That issue is from 2026-07-06 and asks to bump `@v1.6 → @v1.9`; kermit-pa is on `@v1.12`, so it requests a **downgrade** to a version the repo passed, on a project that is now frozen. Same shape as the keystone duplicate closed earlier that day, and nothing had surfaced it because nothing looked. Left open — this phase reports on consumer issues and does not touch them.

## Three defects caught in my own work

**A test that passed against code doing nothing.** The first version of the untracked assertion did `grep -q "untracked"` against a row whose project was named `untracked-1` — so it matched the *project name* and passed before a single line of rendering existed. Fixture renamed to `unfiled-1`, and all five untracked assertions now match the rendered form `· untracked` rather than the bare word.

**A guard with no test, found by mutation.** Six deliberate breakages were run against the finished code; five failed the suite and **one did not** — deleting the "an open bump PR is tracking" guard left every assertion green. `drift-1` was already that exact case and nothing asserted on it. Added as check 42; the mutation is now caught.

**A mutation harness reading a proxy.** That run initially reported all six mutations as passing, because it took `tail -1` of a suite that prints no summary line — so it read the last assertion, which is the same every time, instead of the result. Counting `PASS`/`FAIL` lines gave the real answer. The same defect class the repo keeps recording: verify against the thing itself, not a signal downstream of it.

## A correction to yesterday's lesson

The spec found `(v1.31)` cited in the mock `gh` for a feature that shipped as `PR #105` — and `git show 208d4ee` confirms PR #105 wrote it that way, a guess two versions ahead of the newest tag at the time. A second copy sat in `tests/fleet-pins/run.sh`.

These survived the sweep that `tasks/lessons/2026-09-04-version-numbers-are-claims-not-predictions.md` prescribes, because that sweep grepped for `v1.30` — the version then being claimed — and these said `v1.31`. The lesson now says to sweep for **any version at or beyond the newest tag**, with the grep that finds them, because a prediction is wrong in both directions: the work may get no phase number at all, and the number guessed will belong to something else.

## Scope decisions

- **No consumer issue filed, closed, or edited.** `teelr/kermit-pa#148` is stale and stays open; acting on it is a separate call.
- **No regex widened.** A "while we're here" change risks matching the three near-miss issues that legitimately mention dev-platform.
- **Empty output is a complete answer, not a failure** — a deviation from the spec, which said to treat it as `failed`. A repo with no open issues and no open PRs legitimately returns nothing, and calling that a failure would suppress the untracked marker on exactly the quietest repos, which are the ones most likely to have been forgotten.
