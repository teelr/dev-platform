# v1.27 Consumer Pin Bump — and the inspector that was reading the wrong file

v1.27 Consumer Pin Bump, **closes v1.27** (2026-09-03, `tasks/consumer-pin-bump-spec.md`): the ask was "bump the seven consumers off `@v0.7`." No consumer was on `@v0.7`, and none was on 2026-09-03 when v1.26 wrote that claim into `CLAUDE.md`, `docs/CI-INTEGRATION.md`, `docs/GLOSSARY.md`, `scripts/check-phase-tags.sh`, the consumer template, a ROADMAP entry, a lesson file, and the titles of seven issues filed on repos dev-platform does not own. The pins, read from each repo's default branch:

| Repo | Live pin | Ran `check_version_collision.py`? |
| ---- | -------- | --------------------------------- |
| `teelr/kermit-harness` | `v1.26` | yes — already bumped |
| `teelr/kermit-pa` | `v1.12` | **yes** |
| `teelr/keystone` | `v1.12` | **yes** |
| `teelr/kermit-v3` | `v1.13` | **yes** |
| `teelr/OPIE` | `v1.2` | no |
| `teelr/keystone_prototype` | `v1.0` | no |
| `Osigin-LLC/SQRL` | unverifiable — `gh` 404s on that account | unknown |

So v1.26's sharpest claim — the collision guard "has never run for a single consumer" — was false for three of the six reachable repos. Verified per repo with `gh api repos/<slug>/contents/...`, per tag with `git show <tag>:.github/workflows/taxonomy-check.yml` (`v0.7` → 0 hits, `v1.0` → 0, `v1.11` → 1, `v1.12` → 1, `v1.13` → 1, `v1.26` → 1).

**The `@v0.7` number came from an example `curl` URL in `docs/CI-INTEGRATION.md:26`** that had gone stale nineteen phases earlier. Nobody invented it; it was read from the nearest authoritative-looking thing and propagated. That example now fetches the template from `main`, which carries the current default pin — the staleness trap is gone rather than reset.

**`scripts/fleet-pins.sh` exists to answer exactly this question and was never run — and would have answered wrong.** It read each project's **local working copy**, not the file GitHub Actions runs. Those still differ: OPIE's local file reads `@v1.12` while its live workflow runs `@v1.2`, because an uncommitted `fleet-install-template.sh --force` overwrite sits in its working tree. The inspector now reads the live pin from the default branch (`--source both` by default, `local` for offline runs), treats the live value as authoritative, and reports `⚠ local ≠ live` naming both. An unreachable repo becomes `unverifiable` — a seventh state — and never silently degrades to the local answer: `gh` returns the same 404 for "no such file" and "no access to this repo", so the repo is probed before the file, and SQRL is reported as an unknown rather than as a compliant consumer.

**`keystone_prototype` was a consumer nothing could see.** It has the template and an open issue, but was missing from `monitoring/projects.json`, so no fleet tool had ever reported it — and it is one of only two repos where v1.26's claim was actually true, pinning `@v1.0`, which predates the guard.

## The bug underneath, found by the acceptance test

Change 1's own acceptance test could not run. From a worktree the inspector reported `— not adopted` for all seven consumers, because `projects/` is gitignored — it exists only in the main checkout — while every fleet script derived its root from its own file location. Five scripts, one wrong derivation copied five times, and **none of them errored**: `fleet-gate.sh` would sweep nothing, `fleet-install-template.sh` would create `projects/<name>/.github/workflows/` *inside the worktree* and write a template no CI reads.

v1.25 had already fixed this identical bug for `install.sh` and `verify.sh` — but inline, in those two files, so the fleet scripts became copies five and six instead of sharing it. Extracted to `scripts/lib/main_checkout.{sh,py}`: `REPO` stays the worktree (correct for this repo's own files), `FLEET_ROOT` resolves to the main checkout via `git rev-parse --git-common-dir`, and only relative registry paths are joined onto it — absolute paths, which every fleet test suite uses via `mktemp`, still bypass it entirely.

Pointing `install.sh` and `verify.sh` at the helper was tried and **reverted**: `tests/worktree-default` deliberately copies them plus `uninstall.sh` into a fixture worktree *by themselves*, to test working-tree versions rather than HEAD's, so a sourced sibling is not there — five failures, caught by the gate on the first run. They keep their inline copy, as do `gate-lock.sh` and `check-concurrent-sessions.sh`, which run from the deployed `~/.claude/worktree/` path where `scripts/lib/` does not exist. The helper's header names all four and says why, so the next sweep does not re-try it. "One shared helper" means one for everything that can share it, plus a written reason for each that cannot.

## The pins were stale because of the tag gap, not because consumers ignored asks

`kermit-v3` sat at `v1.13` and the others at `v1.12` — exactly the newest tags that existed while tagging was stopped. Dependabot had already opened bump PRs for three of them (`kermit-v3` PR #362, `kermit-pa` PR #130); it simply had nothing newer to move to. With tagging mechanical since v1.26, Dependabot is the standing fix, and `docs/CI-INTEGRATION.md` now says so — naming which consumers have the `github-actions` block and which bump by hand, that a Dependabot PR still needs merging, and that `fleet-install-template.sh --force` is not a pin-bump tool (it rewrites the whole template, and consumer copies have diverged).

`docs/CROSS-REPO-COMMS.md` records the SQRL account boundary — `repo_slug.py` parses its alias remote correctly, so the slug is right and the *access* is missing, which are different failures — and that a pin-bump issue should carry the consumer's **verified** pin, filed only for consumers without Dependabot.

## Scope decisions

**The consumers are not bumped by this phase, and cannot be.** The Scope rule forbids writing to `projects/`, and the one carve-out rewrites the entire template over files that have diverged from it. Each project's own session opens its one-line PR, as `kermit-harness` did in PR #380. **OPIE's uncommitted working-tree overwrite is left untouched** — discarding another repo's uncommitted work from this session is not this session's call; it goes in OPIE's issue comment. The v1.26 ROADMAP entry and shipped record are **corrected by appended note, not rewritten**: v1.26 set the precedent that historical entries stand as accurate history, and the distinction that matters is that these were not accurate.

28-assertion `tests/fleet-pins/` (11 new, all offline behind a mock `gh`, including drift, unverifiable-vs-absent, and the anchored-regex shadow regression re-run on the live path) plus a new 10-assertion `tests/fleet-worktree/` that builds its own repo and a real worktree of it and asserts the resolution from both — the v1.25 lesson about running the gate from every location it will be run from, made mechanical. Gate at 387 PASS (+27) from the worktree; the main-checkout run is CI's fresh clone, and `tests/fleet-worktree/` asserts both resolutions internally from its own fixture rather than depending on where it runs.
