# v1.25 Worktree Mode Default — dev-platform opts in; the deployment tracks main

v1.25 Worktree Mode Default, **closes v1.25** (2026-09-03, `tasks/worktree-mode-default-spec.md`): worktree mode (v1.4) gives each concurrent session its own copy of the repo, and five of eighteen projects had opted in — but dev-platform had not, which is why two sessions here still shared one checkout and one branch. v1.19 deferred opting in with a hazard flagged: `install.sh` symlinks `~/.claude/*` at repo paths, so installing from a worktree would leave the live deployment pointing into a directory `/merge` later deletes.

**The hazard was real and larger than the deferral said, and measuring it reframed the fix.** Proved with a throwaway worktree before planning: `scripts/verify.sh` run from one exits 1 with **21 failures**, every one the same class — `orphan symlink: ~/.claude/commands/code.md -> /home/rich/dev/commands/code.md`. The deployment was *correct*; only the checker's expectation was wrong, because both scripts derived `REPO` from `BASH_SOURCE` (`install.sh:25`, `verify.sh:14`). Since `gate_fast.sh:119` runs that verify on every gate, **the gate would have gone red on every worktree run** — the actual blocker. So the fix is not "refuse to install from a worktree" but one idea in two places: the live `~/.claude` deployment always tracks the **main checkout**, never a branch. Both scripts now resolve `REPO` through `git rev-parse --git-common-dir` (the derivation v1.20's session detector already used), so symlinks cannot dangle and verify cannot false-fail — from a worktree, a hand-run, or the gate. Swept together per the Derivation Sweep rule (v1.21): same value, same wrong derivation, two scripts, fixed in one change rather than one at a time. It also repaired a second symptom the probe surfaced: `REPO` feeds 14 things in `verify.sh`, including `verify-remotes.sh`'s `${REPO}/projects/<name>` lookups, which had SKIPped every project from a worktree. Verified after: 21 orphans → 0, exit 0, remotes SKIPs gone.

**"Default" is scoped honestly rather than as the title implies.** A true inversion would flip the 13 un-migrated projects into worktree mode with no deps manifest — worktrees missing `node_modules`, worse than branch mode — and v1.19's core finding was precisely that a manifest cannot be invented from outside the project (cross-project writes are forbidden regardless). What changed is the default *experience*: dev-platform opted itself in, and all three scaffolding templates now ship `.claude/worktree-deps`, so **every new project starts in worktree mode from its first commit**. Existing projects add one file from their own sessions. Recorded as a scope decision in `docs/CONCURRENT-DEV.md`, not left looking like a shortfall.

**One behavior change documented rather than hidden:** with the deployment always tracking main, a worktree session's edits to `commands/` or `skills/` are not live in `~/.claude` until merged. That is the safe direction — deployed means shipped, never mid-phase — but it ends the live dogfooding of command edits this repo had relied on all through v1.19-v1.24. Both scripts print a notice when they resolve somewhere other than where they were invoked, so a user meets the change at the moment it applies rather than by surprise.

Three implementation catches. **The gitignore trap, fifth appearance** — `.claude/` is a blanket *directory* ignore, so unlike the four previous occurrences a single `!` re-include would have started tracking every worktree; the correct shape is three rules (re-include the directory, re-ignore its contents, allow just the marker), probed per file before it went in the spec. That probe also **misled once**: a bare `git status` printed a collapsed `?? .claude/`, which looks like success — only `-uall` plus per-file `git check-ignore` showed the truth, and the rule comment now says to verify that way. **A worktree checks out HEAD, not the working tree**, so the first attempt to test the fix from a worktree silently ran the *old* script and reported all 21 failures unchanged; `tests/worktree-default/run.sh` therefore copies the working-tree scripts into the probe worktree after creating it, with a header note saying why. And **the gate caught a Consumer Audit gap the spec missed**: `new-project.sh:89-95` substitutes `{{PROJECT_NAME}}` through an explicit name allow-list, and `worktree-deps` is extensionless, so all three scaffold tests failed with "1 files still contain {{PROJECT_NAME}}" — fixed at the source by adding the name to the find expression rather than by dropping the placeholder.

**The sweep found a third script, and it failed silently.** Applying the Derivation Sweep rule to my own change — grepping for every script with the same `BASH_SOURCE` derivation that also touches `~/.claude` — surfaced `scripts/uninstall.sh`, which the spec had not listed. It removes a symlink only if the target resolves under `${REPO}` (line ~28), so a worktree-derived `REPO` matches none of main's links: proved live, **21 symlinks survived and it still printed "Uninstall complete."** That also broke `tests/install/run.sh`'s verify-after-uninstall assertion from a worktree (expects exit 1, got 0) — so it was a second gate blocker hiding behind the first. Swept with the other two and given its own assertion, which checks the symlink count rather than the exit code, because the exit code was never the problem. Three false positives confirmed and left alone: `gate_fast.sh`'s `REPO` must stay the *invoking* checkout (you want to run the worktree's tests), and the two fleet scripts only use `$HOME` for a telemetry log path, not a repo-derived one.

10-assertion `tests/worktree-default/` suite, running against a real throwaway worktree with a fake `HOME` and trap teardown, including a guard for the non-git `BASH_SOURCE` fallback that nothing else exercises. Gate at 351 PASS (+10).
