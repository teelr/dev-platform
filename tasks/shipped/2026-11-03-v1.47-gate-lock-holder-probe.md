# v1.47 Gate Lock Holder Probe

v1.47 Gate Lock Holder Probe (2026-11-03, `tasks/gate-lock-holder-probe-spec.md`):
fixes issue #140, filed by kermit-v3.

## The problem

kermit-v3's backend health check must not alert while a gate has the dev backend stopped on
purpose (per issue #140, two `/gate fast` runs taking turns raised a false alert on 2026-10-31
at 20:49:51). `shell/worktree/gate-lock.sh` had no public way to ask "is a gate running", so
kermit-v3 parsed the private `gate.lock.holder` note itself (`gate_holder()` in
`projects/kermit-v3/scripts/check_backend_health.sh`, read, not edited). That copy repeated the
pid-alive rule `_gate_lock_describe_holder` already had, and the helper's own path functions
only worked from inside a git working directory, which a cron job or systemd unit does not have.

## What shipped

- `shell/worktree/gate-lock.sh`: `gate_lock_holder_alive [repo-dir] [max-age-minutes]`. Prints
  `pid=N label=L started=S` and returns 0 for a live, recent holder; returns 1 for a missing
  note, dead pid, empty or unparseable `started=`, or a note older than the limit (default
  120 minutes); returns 2 for a limit that is not a whole number. It reads only
  `gate.lock.holder` and never opens, creates or waits on `gate.lock`.
- `_gate_lockfile` and `_gate_lock_holderfile` take an optional directory (default: the
  current directory, so acquire, release and `with_gate_lock` behave as before).
- The note format is parsed in one place, `_gate_lock_holder_field`. `_gate_lock_describe_holder`
  now reads through it, so the waiting message and the probe cannot drift apart.
- `tests/worktree/run.sh`: 13 new checks (6j-6v). Docs: the file header,
  `shell/worktree/README.md` (function table, now four), and `docs/CONCURRENT-DEV.md` (a
  monitor example).

## Verification

- `./scripts/gate_fast.sh`: 576 PASS, 0 FAIL, 0 SKIP (563 before this change).
  `bash tests/worktree/run.sh`: 36 PASS, 0 FAIL.
- Mutation proof, run against the real file edited in place and restored from a copy (diff
  confirmed identical afterwards): dropping the `kill -0` test failed the dead-pid check;
  dropping the empty-`started=` guard failed the empty-started check; dropping the age
  comparison failed the age-limit check; making the probe `: >>` the lockfile failed the
  does-not-create-gate.lock check; ignoring `repo-dir` failed 7 checks (live holder, age limit,
  future note, limit handling, linked worktree, no-lock, held-lock); removing the `10#` prefix
  failed the limit-handling check (`08` is read as an invalid octal number without it).
- The empty-`started=` check uses a `date` shim in `PATH` that answers `date -d ""` with the
  current time, because the real `date -d ""` (midnight today) is only "recent" between 00:00
  and 02:00 and the check would otherwise depend on the time of day.
- While a real `gate_lock_acquire` held the lock in a background job, the probe returned in
  under 2 seconds, named the holder (`label=held`), and the lock was still held afterwards
  (a second `flock -n` on it failed).
- Not exercised: sourcing the file from an actual systemd unit. The file defines only
  functions (no top-level statements), so sourcing has no side effects, but no unit was run.

## Scope honesty

- kermit-v3 still carries its own `gate_holder()` until its session switches to this helper;
  nothing in `projects/` was changed. `~/.claude/worktree/gate-lock.sh` is a symlink to the
  main checkout (`ls -l ~/.claude/worktree/`), so the function is live at merge with no
  `install.sh` step.
- The pid check is a hint: a pid reused by an unrelated process after a gate died reads as
  alive until the age limit passes. `kill -0` fails for another user's pid, so a gate run by a
  different user reads as "no gate".
- A note stamped in the future (clock change) is accepted as recent, matching kermit-v3's copy.
- The spec's line numbers for `gate-lock.sh` were about six lines low; the structure it
  described was correct.
