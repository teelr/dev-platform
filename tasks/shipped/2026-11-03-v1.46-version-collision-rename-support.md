# v1.46 Version Collision Rename Support

v1.46 Version Collision Rename Support (2026-11-03, `tasks/version-collision-rename-support-spec.md`):
fixes issue #147, filed by kermit-v3.

## The problem

`scripts/check_version_collision.py` reported any Roadmap Phase version already on `origin/main`
under a different title as a collision. A deliberate rename therefore failed the
`taxonomy / version-collision` job. kermit-v3 PR #1325 hit it: milestone `v0.579` was renamed on
GitHub from "Azure Second Deployment" to "Azure Deployment for Olsson" and the `ROADMAP.md`
heading was updated to match (details as reported in issue #147; not re-checked against that repo).

## What shipped

- `scripts/check_version_collision.py`: the milestone fetch is now a helper
  (`_milestone_titles()`), called once when there are new or reused versions. A reused version
  is accepted as a rename only when the GitHub milestone for that version already has this
  branch's title. In every other case it is a collision (exit 1): milestone has the old title,
  another title, or no entry, `gh` unavailable, repo slug unresolvable, or the API call failed.
  Those last three print the extra note "milestone lookup unavailable, so a rename cannot be
  confirmed" and never exit 2. New-version handling and messages are unchanged. A collision
  on a reused version now ends with a hint to rename the milestone first.
- `tests/version-collision/run.sh`: 8 new checks (15-22) covering confirmed rename, old title,
  third title, no milestone, `gh api` failure, unresolvable slug, rename plus a clean new
  version (and the same with the lookup down), and a confirmed rename next to a colliding new
  version.
- `docs/CI-INTEGRATION.md`: the troubleshooting row now says to rename the milestone first,
  and states that older pins keep the old behavior; the feature bullet notes the one case
  where an unreachable milestone list fails instead of warning.

## Verification

- `bash tests/version-collision/run.sh`: 0 FAIL after the change; the pre-existing 14 checks
  pass unmodified.
- Mutation proof, run against the real script edited in place and restored from a copy:
  accepting every rename failed 7 checks; accepting a rename when the lookup fails failed 4
  (including both lookup-failure checks); never accepting (old behavior) failed 3, including
  the confirmed-rename check.
- Live read-only call of `_milestone_titles()` against `teelr/dev-platform`: returned 56
  milestones, `v1.45` and `v1.46` present with their expected titles. A rename was not
  exercised end to end against real GitHub; the suite uses the mock `gh`.
- Milestone titles are unique per version in this repo: `gh api ... --jq '.[].title'` with
  version prefixes sorted and `uniq -d` printed nothing.
- `claim_roadmap_version.py` has no reused-version branch (`grep -n reused` on it: no hits),
  so it is unchanged.

## Scope honesty

- Consumers get this only after bumping their pin to the `@v1.46` tag, cut at post-merge.
  kermit-v3 is reported (in issue #147) as pinned to `@v1.32`; that was not re-verified here,
  so PR #1325 stays red until their pin moves.
- Titles are compared as exact strings after the `strip()` both sides already get.
