# v1.22 Gate Lock Visibility

v1.22 Gate Lock Visibility, **closes v1.22** (2026-09-03, `tasks/gate-lock-visibility-spec.md`): running three or four sessions on one project made `/gate fast` feel broken. The gate lock was doing its job — stopping two runs fighting over the same port — but doing it in total silence, so a session queued behind another was indistinguishable from one that had hung. The waiting was never the problem; not knowing whether it was waiting was. A contended acquire now names the holding pid and when it started, then reports how long it waited. An uncontended acquire prints nothing, deliberately: a message on every gate run is noise, and noise on the common path is how a real warning gets ignored. **What this deliberately does not do is narrow the lock**, which was the first instinct and is wrong. kermit-v3 and Keystone both hold it across the whole stop→pytest→restart window because the gate stops the backend precisely so pytest can bind those ports itself; the port is exclusive for the entire test run, and shrinking the lock would trade a visible wait for two runs racing on one port. The way to wait less is ordering — run the lock-free checks before acquiring — not scope. Reading the consumers also turned up why the existing API went unused: `with_gate_lock` wraps a single command and cannot express hold-across-a-region, so both projects reached past it for the private `_gate_lockfile` and hand-rolled the same `exec 9>…; flock 9; …; exec 9>&-` block, byte-for-byte identical down to the comments. That is the duplication shape v1.21 promoted to the Derivation Sweep rule, so this ships `gate_lock_acquire`/`gate_lock_release` — the shape they needed — with the messaging built in, and post-merge files a handoff issue on each so they adopt it from their own sessions. Holder metadata lives in a sibling `.holder` file rather than the lockfile, because `9>` truncates at open before `flock` runs and a waiter would otherwise erase the holder's stamp; it is advisory, since `flock` releases on death and the file outlives its process. One bug in my own code, caught by running it rather than reasoning about it: `exec 9>"$lf" 2>/dev/null` applies every redirection to the shell permanently, because `exec` has no command — it silenced stderr for the whole run and swallowed the announcements being added. A test-side variant of the same scope mistake made a "must be silent" assertion pass vacuously. +8 assertions, gate at 320 PASS.
