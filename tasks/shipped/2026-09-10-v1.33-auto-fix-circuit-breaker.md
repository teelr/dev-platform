# v1.33 Auto-Fix Circuit Breaker — the verify → fix loop gets a bound

v1.33 Auto-Fix Circuit Breaker, closes v1.33 (2026-09-10, `tasks/auto-fix-circuit-breaker-spec.md`, [issue #118](https://github.com/teelr/dev-platform/issues/118)): `/code`'s verify → fix → re-verify loop had no bounded-retry or repeated-failure circuit breaker — nothing stopped a fix attempt from cycling against the same failure indefinitely, burning cost and wall-clock time silently instead of escalating. The issue flagged this deliberately as "not a spec, not a commitment to build it as described," so the scoping call — which loops, what bound, what happens on trip — was made at `/plan` time.

## What shipped

**A prose fix, not a code fix.** `/code` is an agent following written instructions, not a script with a call stack — there's no `for` loop to instrument. The circuit breaker is a rule `/code` now follows: count attempts, recognize when a fix reproduced the prior failure, and stop rather than keep guessing.

**Swept for the same shape before deciding scope**, per the Derivation Sweep rule: the verify → fix → re-verify pattern appears three times across `commands/code.md` and `commands/review.md`. Step 3 (per-Change) and Step 5 (end-to-end) both retry the *same* failure across repeated fix attempts — exactly what the issue describes, and both now bounded. `commands/review.md` Step 4 (the SECURITY/BUG/COMPLIANCE/QUALITY fix pass `/code` Step 9 runs) is structurally different — it fixes each already-identified issue once and re-verifies once, never retrying a fix against a persisting failure — so it carries none of the unbounded-cycling risk and is left untouched, called out explicitly in the new Rules subsection so a future reader doesn't wonder why it wasn't covered.

**The bound, added to `commands/code.md`:**

- **Attempt cap** — stop on the 3rd consecutive verification failure for the same Change (Step 3) or end-to-end pass (Step 5), i.e. after 2 fix attempts have both failed.
- **No-progress cap** — fires earlier: stop immediately if a fix attempt is followed by a re-verification failure with the same signature as the one before it (same command, same file/line, same error/assertion). An unchanged failure means the fix changed nothing.
- **Escalation** — either cap trips the same way: stop the whole `/code` run, leave the broken state as evidence rather than reverting it, and report which Change/check is blocked, the exact failing output, and every fix attempted — in place of Step 10's normal "Ready for `/gate fast`" ending.

This is the same STOP-and-wait discipline `settings/claude-global.md` already applies between workflow steps, now also applied inside a single `/code` turn's own retry loop.

`skills/WORKFLOW_MANUAL.md`'s `/code` Key Behavior list mirrors the same bound for a reader learning the workflow from the manual.

## Scope decisions

- **`commands/review.md` Step 4 is not bounded** — it was never the loop the issue described (see above). Bounding it anyway would have been scope creep against a loop that was never the problem.
- **No per-language or per-project exception to the attempt cap.** Uniform across every Change and every stack `/code` might touch.
- **No mechanical test/detector.** There's no code artifact to grep for compliance against — `/code`'s adherence to a bounded retry is a matter of it following its own instructions correctly on a live run, the same class of thing as Step 6's Adversarial Self-Review (also untested by a suite).
- **No change to the workflow chain string.** `/plan → /code → /review → /gate fast → commit → push → /pr → CI → /merge → post-merge` is unchanged; verified `audit-project-drift.sh --project dev-platform` still reports CLEAN.
