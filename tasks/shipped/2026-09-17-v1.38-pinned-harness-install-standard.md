# v1.38 Pinned Harness Install Standard

v1.38 Pinned Harness Install Standard (2026-09-17, `tasks/pinned-harness-install-standard-spec.md`):
closes [issue #122](https://github.com/teelr/dev-platform/issues/122) — decide the install
strategy for the shared `kermit` conda env (pinned wheel vs. editable vs. per-project envs).
Decided: pinned wheel/sdist.

## The verified problem

- The shared `kermit` conda env installs `kermit-harness` **editable**, against the live
  sibling checkout at `/home/rich/dev/projects/kermit`, via `pip install -e
  /home/rich/dev/projects/kermit` — run by hand as part of each consumer's own pin-bump
  survey, never by an automated script (verified: `kermit-v3/docs/roadmap.md:372`).
- The three active consumers do NOT share one pin style: `kermit-v3` exact-pins
  (`kermit-harness==4.167.0`), `keystone` range-pins (`kermit-harness>=4.105.2,<5.0.0`),
  `kermit-pa` (frozen) range-pins with extras
  (`kermit-harness[audio,bm25,reranker,documents]>=4.91.0,<5.0.0`). None of the three pins
  constrain what's actually *installed* — only what's *declared*.
- `teelr/kermit-harness` already cuts a Release on nearly every commit (10 releases,
  `v4.158.0`–`v4.167.0`, over roughly two days), automated by its own `make release
  VERSION=X.Y.Z` (`Makefile:452-487`) — but attaches **no build artifact** to any of them
  (`gh release view --repo teelr/kermit-harness --json assets` on `v4.167.0`: `"assets":
  []`). There is nothing installable except the live tree.
- `kermit-v3` and `keystone` have each independently built their own deploy-time
  mitigation (`prod-deploy.sh` runs `pip wheel "${KERMIT_SRC}" --no-deps` against the same
  sibling checkout) — duplicated logic that protects only the prod build, not the shared
  dev env where the gate actually goes red.
- Measured cost: three harness releases in about a day each turned every live `kermit-v3`
  session's gate red simultaneously; two sessions independently started the same fix
  before noticing the duplicate work; the identical drift then hard-blocked a real
  `kermit-v3` prod-deploy build the same day this spec was written (pin bump `4.165.0` →
  `4.167.0`).

## The decision

Pinned wheel/sdist over an editable tree or per-project conda envs. Per-project envs alone
don't decouple anything — an editable install against the SAME sibling checkout stays
live regardless of how many envs point at it. A pinned artifact is the only option where
each consumer's env, not just its deploy build, installs one version and stays there
until it deliberately reinstalls.

## What shipped

- **`docs/CROSS-REPO-COMMS.md`**: new "Runtime install: pinned wheel, not the live tree"
  section, documenting the verified problem, the decision, and the target shape —
  `teelr/kermit-harness` attaches a wheel (and sdist) to every Release it already cuts
  (it already declares a `hatchling` build backend, so `python -m build` needs no new
  packaging config), and each consumer installs its own pinned version directly from
  that Release asset instead of the live tree. Also adds one bullet to the existing
  `## Migration status` list tracking this as DECIDED.
- **That is the only Change.** Per the no-cross-project-writes rule, this session does not
  edit `teelr/kermit-harness`'s `Makefile`, any consumer's `prod-deploy.sh`, or any
  env-setup script.

## A real correction caught before it shipped

An early pass at reading each consumer's `pyproject.toml` misattributed one file's content
to the wrong project in a batched multi-command read — a `pip install -e` survey comment
that actually belonged to `kermit-v3`'s file appeared, in a combined `find`+`cat`+`grep`
call's result, alongside text that read as Keystone's. Re-running the check as three
separate, single-target `grep` commands (one file, one pattern, one call each) resolved
it cleanly and surfaced the real, load-bearing fact: the three consumers do NOT share one
pin style. Lesson:
`tasks/lessons/2026-09-17-dont-trust-attribution-in-a-batched-multi-file-read.md`.
