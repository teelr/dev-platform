# v1.42 Actions Hardening

v1.42 Actions Hardening (2026-10-30, `tasks/actions-hardening-spec.md`): closes the GitHub
Actions and Dependabot items of `issue #131`, left over from the 2026-10-30 security review of
this public repo.

## The verified problem

- Every third-party action was pinned to a moving tag: ten `uses:` lines across `gate.yml` (1),
  `pages.yml` (5) and `taxonomy-check.yml` (4) (`grep -rn "uses:" .github/workflows`). The spec
  said nine; it is ten.
- Dependabot was off: `gh api repos/teelr/dev-platform/vulnerability-alerts` returned 404 and
  `automated-security-fixes` returned `{"enabled":false}`. There was no `.github/dependabot.yml`,
  so nothing would ever propose an update to a pinned action.
- `taxonomy-check.yml` expanded `${{ github.job_workflow_ref }}` inside a shell `echo` (lines 74
  and 103; `issue #131` quoted ~57-59 and ~94-96, which were wrong).
- The `taxonomy` job had no `permissions:` block; `gate.yml` already had one from `PR #129`.
- `gate_fast.sh`'s YAML check covered only `.github/workflows` and `extensions/github-actions`.

## What shipped

- All ten `uses:` lines pinned to a 40-character commit SHA with a version comment:
  `actions/checkout` `11d5960a...` (v4.4.0), `configure-pages` `1f0c5cde...` (v4.0.0),
  `jekyll-build-pages` `44a6e6be...` (v1.0.13), `upload-pages-artifact` `56afc609...` (v3.0.1),
  `deploy-pages` `d6db9016...` (v4.0.5). The SHAs were resolved at planning time and again at
  `/code` time and were identical.
- `.github/dependabot.yml`: the `github-actions` ecosystem, weekly, no labels.
- `taxonomy-check.yml`: `job_workflow_ref` now goes through `env: JOB_WORKFLOW_REF`, never
  expanded in the script body; `permissions: contents: read` on the `taxonomy` job (what the
  `version-collision` job already requests). No top-level block was added.
- New `tests/actions-pinning` suite, 9 PASS (pins, Dependabot config, no `${{ }}` in `run:`,
  permissions), each check also run against a violating fixture so it is shown able to fail;
  `gate_fast.sh` now counts `.github/dependabot.yml` in its YAML check (5 files before, 6 now).
  Gate fast: 538 PASS, 0 FAIL, 0 SKIP.
- The consumer template's "dev-platform itself does not run it" note is corrected, and
  `docs/CI-INTEGRATION.md` explains the SHA pinning.

## Findings

- `taxonomy-check.yml` is the workflow every consumer calls and this repo's own CI never runs
  it, so the real proof of the `env:` change is the first consumer run after the next tag. What
  was checked: `tests/reusable-workflow` (7 PASS), and the changed shell snippet run by hand
  against `teelr/dev-platform/.github/workflows/taxonomy-check.yml@refs/tags/v1.31`, which
  printed `ref=refs/tags/v1.31`.
- The "no expressions in `run:`" check is stricter than the spec: it forbids any `${{`, not only
  `${{ github.`, because `inputs.*` and `steps.*` are caller-controlled too.
- This PR changes `pages.yml` and `docs/CI-INTEGRATION.md`, both under the Pages workflow's path
  filter, so merging triggers a `deploy-pages` run that exercises the pinned Pages actions.

## Not covered

- The repo-level settings are NOT changed by this phase's code: Dependabot alerts and security
  updates, and mandatory SHA pinning (`sha_pinning_required`), are the post-merge step and each
  asks the user first. `sha_pinning_required` must only be turned on after the pins are merged.
- It is unverified that Dependabot rewrites a SHA pin together with its `# v` comment; confirm
  from its first run.
- `persist-credentials: false` on the checkouts was left out: its effect on the reusable
  workflow cannot be exercised by this repo's CI.
