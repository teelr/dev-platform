# v1.26 Version Reference Discipline — and the twelve-phase tag gap underneath it

v1.26 Version Reference Discipline, **closes v1.26** (2026-09-03, `tasks/version-reference-discipline-spec.md`): three identifiers reference shipped work and nothing said which to use when. `v1.25` is a **Roadmap Phase** — a unit of planned work claimed atomically at `/plan`, matching a milestone. `#92` is a **GitHub PR number** — sequential, sharing a number space with issues, no semantic meaning. `v1.13` as a **git tag** is a third thing: the only one a consumer can pin. Prose jumped between them because each was written by whatever felt natural that day, and a reader could not tell whether two references meant the same thing. All three can carry the string `v1.25` and mean different objects, which is precisely why the rule was needed.

**Chasing the inconsistency surfaced a functional gap.** Tagging stopped at v1.13 — twelve phases ago — so v1.14 through v1.25 are unpinnable. Meanwhile all seven consumer projects pin `@v0.7`, whose `taxonomy-check.yml` runs only `check_spec_taxonomy.sh` and does **not** include `check_version_collision.py` (verified with `git show v0.7:...`). So the version-collision guard shipped in v1.11 and fixed in v1.12 and v1.13 has **never run for a single consumer** — despite v1.11's ROADMAP entry stating every consumer would get it "without any local wiring." True of the workflow on `main`; false of every tag anyone was pinning.

**Why it died silently is the transferable part.** The practice *was* documented — `docs/GLOSSARY.md`'s "Cut release" entry says to tag at the merge commit closing a phase. But it lived in a reference doc nobody executes from, while closing the milestone is a mechanical post-merge sub-step. Same repo, same phase-completion moment, two practices: the one wired into the runbook has happened every single time, the one requiring memory stopped after v1.13. So this phase applies the pair v1.10 already proved for milestones — a mechanical step in `commands/merge.md` and `CLAUDE.md`, plus `scripts/check-phase-tags.sh` as the backstop. Run on this branch it reports exactly the real gap: 12 of 35 complete phases untagged, v1.14 through v1.25, with correct titles.

Ships the citation rule in `CLAUDE.md` (phase version canonical, PR number as provenance only, tag as what consumers pin), Glossary entries for **PR number** and **Release tag** plus an amended "Cut release" pointing at the now-mechanical step, and the consumer template default bumped `@v1.12` → `@v1.26`.

**Two scope decisions, recorded so they do not read as oversights.** The twelve missing tags are deliberately NOT backfilled — consumers need one recent tag, not an exact historical phase, and mis-tagging twelve merge commits is worse than leaving them visible to the detector. Historical ROADMAP entries are left alone: "Released `v1.11`" is accurate history, and rewriting the record to look consistent would make it less true.

**The gate caught a spec gap that was a fourth and fifth copy of the same value.** `--pin` broke with rc=2 because `scripts/fleet-install-template.sh` hardcoded `DEFAULT_PIN="v1.12"` — and its own error message said "Update DEFAULT_PIN in this script", a maintenance step nobody had remembered since v1.12. `--help` hardcoded it again, and `tests/fleet-install/run.sh` hardcoded `@v1.10`, which had gone stale at the v1.12 bump and made half that assertion vacuously true — it asserted the absence of a version that was no longer the default anyway. Rather than bumping five copies, the template's `uses:` line became the single source: the script derives the default from it, the help text stops naming a version, and the test reads it too. Derivation Sweep rule, applied to the thing the phase was already about.

One implementation detail worth the comment it got: that derivation must be **pure bash**, no `sed`. It runs before the required-tools gate, and the tools-gate test invokes the script with `PATH=/tmp` to prove that gate fires — any external command there would fail first and mask it. The first attempt used `sed` and turned a passing tools-gate test into a failure with the right exit code and the wrong message.

9-assertion `tests/phase-tags/` suite, offline against fixture repos, including the dual-form regression (list AND heading roadmap forms — the v1.12 bug, which reports clean while checking nothing) and a guard that an in-flight untagged phase is not a finding. The suite never reads dev-platform's own tags, so cutting a real release cannot change its result. Gate at 360 PASS (+9), verified from both the main checkout and a worktree.

## Correction (2026-09-03, v1.27)

**The consumer-pin claim above is false.** No consumer pinned `@v0.7`, and none did
on the day this was written. Read from each repo's default branch on GitHub:

| Repo | Live pin at the time | Ran `check_version_collision.py`? |
| ---- | -------------------- | --------------------------------- |
| `teelr/kermit-harness` | `v1.26` | yes |
| `teelr/kermit-pa` | `v1.12` | **yes** |
| `teelr/keystone` | `v1.12` | **yes** |
| `teelr/kermit-v3` | `v1.13` | **yes** |
| `teelr/OPIE` | `v1.2` | no |
| `teelr/keystone_prototype` | `v1.0` | no |
| `Osigin-LLC/SQRL` | unverifiable — `gh` 404s on that account | unknown |

So "the guard has never run for a single consumer" was wrong for three of the six
reachable repos; it runs on kermit-pa, keystone and kermit-v3, and has since their
`@v1.12`/`@v1.13` bumps. Verified per repo with `gh api repos/<slug>/contents/.github/workflows/dev-platform-gate.yml`,
and per tag with `git show <tag>:.github/workflows/taxonomy-check.yml | grep -c check_version_collision`
(`v0.7` → 0, `v1.0` → 0, `v1.11` → 1, `v1.12` → 1, `v1.13` → 1, `v1.26` → 1).

**Everything else in this record stands.** The tag gap was real, the twelve
missing tags were real, and the mechanical post-merge step plus
`check-phase-tags.sh` were the right fix. The tag gap is also the actual reason
the pins were stale: `v1.13` was the newest tag in existence, so consumers — and
Dependabot, which had opened bump PRs for three of them before — had nothing
newer to move to.

**Why it went unnoticed** is the part worth keeping. `scripts/fleet-pins.sh`
exists to answer exactly this question and was never run; the `@v0.7` number came
from an example `curl` URL in `docs/CI-INTEGRATION.md`. And running it would not
have helped: it read each project's **local working copy**, not the file GitHub
Actions runs. Those still differ for OPIE — local `@v1.12`, live `@v1.2` — because
an uncommitted `fleet-install-template.sh --force` overwrite sits in its working
tree. v1.27 fixes the inspector and corrects the seven issues this claim reached.
