# v1.39 Settings Permission Tightening

v1.39 Settings Permission Tightening (2026-10-30, `tasks/settings-permission-tightening-spec.md`):
a security review of the public repo found no leaked secrets, but the permission baseline in
`settings/settings.json` allowed arbitrary shell, network and remote access without a prompt.
This phase narrows it and fixes the reason a baseline edit could not narrow it.

## The verified problem

- The baseline allowed `Bash(bash *)`, `Bash(sh *)`, `Bash(source *)`, `Bash(xargs *)`,
  `Bash(curl *)`, `Bash(ssh *)`, `Bash(scp *)`, `Bash(kill *)`, `Bash(systemctl *)` and
  `Bash(apt *)`, unscoped env-var prefixes such as `Bash(PGPASSWORD=*)`, and unrestricted
  `Read` of `/home/rich/**`. The only deny rules were two `sudo rm -rf /` literals.
- `scripts/merge_settings.py` unions permission lists, so deleting an entry from the baseline
  never removed it from `~/.claude/settings.json`. Checked against the live file: it held 320
  allow entries, including every broad one above. A tightened baseline alone would have
  changed nothing on this machine.

## What shipped

- `merge_settings.py --retract <file>`: removes exact-match strings from the live
  `permissions.allow` after the union. Exact equality only, so a retract of `Bash(bash *)`
  leaves `Bash(bash ~/.claude/worktree/*)` alone. A baseline allow entry that is also
  retracted exits 2; so does a malformed, wrong-shape or missing retract file.
  `install.sh` passes `settings/permissions-retract.json`; `verify.sh` reports any retracted
  entry still in the live file.
- A tightened `settings/settings.json`: scoped env-var prefixes, read-only `systemctl`,
  `pm2`, `dpkg`, `tailscale` and `code` forms, narrow allows for the workflow's own scripts
  (`bash ~/.claude/worktree/*`, `bash /home/rich/dev/scripts/*`), an `ask` list (`sudo`,
  `git push`, destructive git and docker commands), and a much larger `deny` list (force
  push, `--no-verify`, `curl | sh`, `rm -rf` on root and home, reads of `~/.ssh`, cloud
  credentials and `.env` files, edits to `~/.ssh`, `.bashrc`, `.profile`).
- `settings/permissions-retract.json`: 36 entries, generated by diffing the old baseline
  against the new one and intersecting with the live file, plus the accumulated broad grants.
- `tests/settings-baseline/run.sh` (6 checks) and 6 new fixtures in `tests/merge-settings/run.sh`.

## Findings

- The Claude Code docs confirm the order is deny, then ask, then allow, and that an `ask`
  rule prompts even when a narrower `allow` matches. That is why `bash *`, `rm *`, `kill *`
  and `curl *` are not in `ask`: they would override the narrow allows the workflow needs.
- `sudo *` is in `ask`, not `deny`: the live file has about a dozen working `sudo` grants
  that a deny would have silently killed.
- Auto mode (`defaultMode: auto` in the live file) drops broad allow rules such as
  `Bash(python*)` on entry, per the docs, so some of the exposure was already narrower in
  practice than the file suggests.
- Whether a literal `~` in a `Bash(...)` pattern matches command text is inferred from the
  docs, not stated. UNTESTED until the first `/plan` or `/code` run after install.

## Not covered

- `python *`, `node *`, `npm *`, `npx *`, `pip *`, `go *`, `cargo *` and `./scripts/*` stay
  allowed and can run arbitrary code. Claude Code's sandbox is the real boundary and is not
  configured here.
- `kill "${_pid}"` in `commands/merge.md` now prompts; it was not given a narrow allow.
- The other ~300 accumulated live grants (one-off `kill -9 <pid>`, keystone worktree `sudo`
  paths) are not pruned.
- Takes effect on the machine only after the user runs `./scripts/install.sh settings`.
