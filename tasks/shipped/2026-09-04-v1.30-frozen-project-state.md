# v1.30 Frozen Project State — one boolean was doing two jobs

v1.30 Frozen Project State, **closes v1.30** (2026-09-04, `tasks/frozen-project-state-spec.md`): `monitoring/projects.json` had one flag, `enabled`, deciding two unrelated things — whether the fleet **runs a project's tests**, and whether the fleet **chases its dev-platform pin**. For most projects those answers agree. For kermit-pa they are opposite, and the day before this phase that conflict was papered over with a 101-word `notes` string explaining in prose why a row would never move.

kermit-pa is deployed and still serving production; kermit-v3 supersedes it, and its last feature work was 2026-07-27. Disabling it would have stopped `fleet-gate.sh` sweeping its test suite — the one automated signal left on something running in prod. Leaving it enabled meant `fleet-pins.sh` reporting `⚠ 17 minor behind` forever, next to projects where that number is a call to action.

Three states exist in the registry and only two were expressible:

| State | Example | Run its tests? | Chase its pin? | Before v1.30 |
| ----- | ------- | -------------- | -------------- | ------------ |
| Active | keystone, kermit-v3 | yes | yes | `enabled: true` |
| **Deployed, frozen** | **kermit-pa** | **yes** | **no** | **not expressible** |
| Dormant / deprecated | OPIE, atlas | no | no | `enabled: false` |

## What shipped

**`frozen: true`, additive and defaulting to false.** A tri-state `status: active|frozen|disabled` reads better on a blank page, but six consumers parse `enabled` today and a rename touches all of them for no behavioural gain. An absent `frozen` means false, so every pre-v1.30 registry keeps working untouched — asserted in the suite, not assumed.

**The flag is not one check. It is six decisions, and they genuinely differ.** The rule applied to each: *does this operation still mean anything on a repo nobody will open a PR against?*

| Consumer | On `frozen: true` | Why |
| -------- | ----------------- | --- |
| `scripts/fleet-gate.sh:117-124` | **still sweeps** — comment only, filter untouched | it is deployed; a broken test is the thing you want to hear about |
| `monitoring/fleet_dashboard.py:245` | **still lists**, row marked `(frozen)` | a months-old "Last commit" should read as expected, not as a project that died |
| `monitoring/fleet_pins.py:487` | pin still read, status `frozen`, no staleness delta | `dev-platform-gate` fires only on PRs, and a frozen repo raises none |
| `scripts/check-migration-coverage.sh:184` | row reads `FROZEN (skipped)` | the lessons convention prevents *future* concurrent appends; there will be none |
| `scripts/audit-project-drift.sh:102` | skipped, **named in the summary** | chain drift only matters to someone about to follow the chain |
| `scripts/fleet-install-template.sh:165` | refuses, with its own message | it mutates a consumer repo; a fresh pin would gate PRs nobody will raise |

Two rules govern the edges. **`unverifiable` beats `frozen`** in `fleet_pins` — a failed read is a fact about the tool, and a fact about the project must never mask it. And **`enabled: false` beats `frozen`** everywhere — `frozen` qualifies an *enabled* project, so the combination is contradictory and is now rejected outright rather than left as a precedence rule to remember.

**Nothing is dropped silently.** Every skip is printed: a `FROZEN (skipped)` row, a named summary line. A project vanishing from a report with no explanation is indistinguishable from a broken filter — the vacuous-output shape this repo keeps rediscovering.

**The pin is still read.** Only the *judgement* is suppressed. kermit-pa's row still shows `v1.12` in both Pin columns and still reports drift if the local copy ever disagrees with its default branch; that is a repo-state problem, unrelated to pin currency.

## The two things the exploration forced in

**The registry schema was documented nowhere.** `monitoring/README.md` covered telemetry and never described `projects.json`; `gate_cmd`, `enabled` and the ad-hoc `notes` field were defined only by the code reading them. Adding a seventh field to an undocumented schema would have compounded that, so the schema is now written down — field table, the main-checkout path rule, the per-consumer `frozen` table, and the precedence rule stated once.

**Nothing validated the registry.** `scripts/check-registry.sh` now does, wired into `gate_fast.sh`. What it catches:

- A **missing `enabled`** — previously read as false-if-absent by every consumer, silently removing a project from the entire fleet with no error anywhere.
- A **string `"true"`** where a boolean belongs. Not pedantry: given `"enabled": "false"` the bash consumers' `jq 'select(.enabled == true)'` excludes the project while Python's `entry.get("enabled", False)` includes it — a non-empty string is truthy. One registry, two answers.
- `enabled: false` + `frozen: true`, duplicate names, and a `gate_cmd` whose script is missing from its checkout.

**Its first run found a bug in itself, not in the registry.** It reported kermit's `gate_cmd` as a missing `make` script — kermit's gate is `make check`, a PATH command, not a repo-relative path. A checker inventing a violation is worse than one check fewer, so the two shapes are counted separately and only the path-shaped form is asserted. The live registry now reports `7 verified, 1 skipped (no checkout), 1 not a repo path`.

**It reports coverage rather than degrading to SKIP.** The `gate_cmd` leg depends on `projects/`, which is gitignored and absent on every CI runner — the same situation that made `check_env_leak.sh` exit 0 having read nothing. But four of the five checks read the tracked registry file, which is always present, so a whole-script SKIP would hide four checks that really did run. This is a deliberate divergence from `check_env_leak`'s three-way pattern, recorded at the wiring site.

## Verification

Every consumer probed against a three-entry fixture (active / frozen / disabled) **before** any code changed, to establish what "unchanged" means — all six treated the frozen entry identically to the active one. Then re-probed after.

`tests/frozen-state/run.sh`, 18 assertions, offline. **Then mutation-tested**: eight deliberate breakages — one per consumer, plus the validator, plus a "skips correctly but silently" variant — each confirmed to make the suite fail. A passing assertion proves nothing until it can fail, and the first pass of that exercise covered only five of the six consumers; `audit-project-drift.sh` had no mutation until the count in this record was checked against what was actually run. The assertion that matters most is #4, *fleet-gate still sweeps a frozen project*, because the plausible wrong "consistency fix" here removes the only automated signal on a project in production.

Against the real fleet:

```text
./scripts/fleet-gate.sh --project kermit-pa   → PASS (11s) — still swept
./scripts/fleet-pins.sh                       → kermit-pa: v1.12 / v1.12 / "— frozen (deployed, not developed)"
                                                 every other row unchanged
./scripts/fleet-status.sh                     → "kermit-pa (frozen) | main | 2026-08-12 (22d)"
./scripts/check-migration-coverage.sh         → kermit-pa: FROZEN (skipped)
./scripts/audit-project-drift.sh              → "Skipped (frozen — deployed, not developed): kermit-pa."
./scripts/fleet-install-template.sh --project kermit-pa → exit 1, frozen-specific message
./scripts/fleet-install-template.sh --project OPIE     → exit 1, disabled message, unchanged
./scripts/check-registry.sh                   → 9 entries conform
./scripts/gate_fast.sh                        → 430 PASS / 0 FAIL / 0 SKIP
```

## Seven stale `v1.30` citations, found and fixed

Grepping the codebase before writing the spec turned up seven comments citing **v1.30** for work that shipped as chore PRs — `PR #101` (the `check_env_leak` gate wiring) and `PR #102` (the second-`gh`-account fallback). Neither was a Roadmap Phase. With v1.30 now legitimately claimed for this phase, the same string meant two different things in one repo — precisely the ambiguity v1.29 shipped a rule against, appearing in code comments a week later.

Fixed in `scripts/check_env_leak.sh`, `scripts/gate_fast.sh`, `monitoring/fleet_pins.py` (×2), `tests/fleet-pins/run.sh`, `tests/fleet-pins/fixtures/mock-bin/gh`, and `CLAUDE.md`. A chore has no phase version, so the correct citation is its PR number.

The lesson is narrower than "cite carefully": **a version number is only safe to write once the version is claimed.** These were written while v1.29 was the newest tag and v1.30 was the obvious next one — a prediction, recorded as fact.

## Scope decisions

- **kermit-pa is the only project marked frozen.** OPIE stays `enabled: false` (dormant but revivable — a different state), atlas stays deprecated.
- **`enabled` is not replaced.** Additive only.
- **No consumer repo is touched.** This changes how dev-platform *views* its consumers; nothing in any consumer repo changes.
