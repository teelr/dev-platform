# v1.44 Docker And Fuser Grants

v1.44 Docker And Fuser Grants (2026-11-01, `tasks/docker-fuser-grants-spec.md`): follow-up to
v1.43. Pruning the live `~/.claude/settings.json` cannot fix a broad grant that the tracked
baseline itself carries, because `scripts/install.sh settings` union-merges the baseline back in.

## The verified problem

- `settings/settings.json` allowed `Bash(docker *)`, `Bash(docker-compose *)` and
  `Bash(fuser *)` with no prompt (read from the file at planning time). `docker run` can mount
  the host root or run privileged, which is root on the host; `fuser -k` kills whatever owns a
  port.
- Both scaffold templates (`scaffolding/go-service`, `scaffolding/python-agent`) copied the same
  two docker entries into every new project (`grep -rn 'docker \*' scaffolding`).

## What shipped

- `settings/settings.json`: the three broad allows are gone. Docker is now a list of 21 specific
  verbs (`ps`, `logs`, `inspect`, `images`, `image ls/inspect`, `network ls/inspect`,
  `volume ls/inspect`, `info`, `version`, `port`, `exec`, `start`, `stop`, `restart`, `tag`,
  `build`, `manifest inspect`, `compose *`), so an unlisted verb prompts. Eight new `ask` entries:
  `docker run *`, `docker cp *`, `docker compose run *`, `docker compose * run *`, and four for
  `docker build` with `-o` or `--output` (`docker build -o*`, `docker build --output*`,
  `docker build * -o*`, `docker build * --output*`). `fuser` has no entry, so `fuser -k` prompts.
  The build entries came from the by-hand security review of the staged diff: `-o`/`--output`
  (present in `docker build --help`) makes BuildKit write the result into a host directory,
  which sidesteps the `Edit`/`Write` denies on `~/.ssh` and shell profiles. None of the 6 past
  `docker build` commands used either flag (`grep -E '^docker build'` over the extracted file).
- `settings/permissions-retract.json`: `Bash(docker *)`, `Bash(docker-compose *)` and
  `Bash(fuser *)` added, so machines that already hold them lose them on the next install.
- `tests/settings-baseline`: the three entries join the banned list; new checks that the four
  `ask` entries exist and that `docker exec/ps/logs/build` and `docker compose *` stay allowed;
  the existing "ask holds nothing that overrides a workflow allow" check now covers
  `docker exec/build/compose`. Each new check was run against a mutated copy of the baseline in
  the session scratchpad (re-added `docker *`, dropped `docker exec *` and `docker run *`, put
  `docker build *` in `ask`) and failed there; it passes on the real baseline. 8 PASS, 0 FAIL.
- The two scaffold templates now allow `docker compose *`, `docker ps*` and `docker logs *`
  instead of `docker *` and `docker-compose *`.
- `settings/README.md` documents the stance and records the mid-pattern `ask` wildcard as
  UNTESTED.

## Findings

- Usage, from 74,488 Bash commands extracted from `~/.claude/projects/*/*.jsonl` (grep on lines
  starting with the command): `docker exec` 629, `docker run` 39 (0 with `--privileged`, `-v /:`,
  `docker.sock`, `--pid=host` or `--net=host`), `fuser` 0. The transcripts include closed
  worktrees, so the counts are higher than one repo's.
- `docker exec` stays allowed on purpose. It is arbitrary code in a container, so this does not
  make a session safe; it removes the unprompted routes to root-on-host and to port-kills.
- `docker run` prompting was chosen by the user at planning time over the alternative of keeping
  it allowed behind deny rules for host-escape flags, which are text matches and easy to sidestep.

## Scope honesty

- Not yet deployed. `./scripts/install.sh settings` changes the live permissions and is a
  post-merge step that needs the user's go-ahead.
- UNTESTED: whether `Bash(docker compose * run *)` matches `docker compose -f x run svc`, and
  whether auto mode (`defaultMode: auto` in the live file) already dropped `docker *` before
  this change. The post-merge step probes the first.
- Known gap: `docker compose *` is allowed, so `docker compose up` on a compose file that
  declares a privileged service or a host mount is equivalent to `docker run` with no prompt.
  Only `compose run` is covered. Closing it needs a different design (for example allowing
  specific compose verbs per flag shape), not planned.
- Left alone: `Bash(curl *)` in both scaffold templates, and any project's own settings.
