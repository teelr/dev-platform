# v1.36 Gate Release Tier — the missing `/gate release` entry point for dev-platform

v1.36 Gate Release Tier (2026-09-15, `tasks/gate-release-tier-spec.md`): `commands/gate.md` already
documented a three-tier contract (`fast`/`full`/`release`) and reported "not available" for the
latter two since dev-platform had never shipped `scripts/gate_full.sh` or `scripts/gate_release.sh`.
This ships the second one.

## Design decisions

- **No `gate_full.sh`.** `CLAUDE.md`'s "full" tier is framed for kermit-harness's concurrency/
  load-testing shape (threads, async interop, backend integration) — dev-platform has no such
  category, so building an empty placeholder would be a check that validates nothing. dev-platform's
  real shape is two tiers: `fast` (every commit) and `release` (before a version bump).
- **Scope narrowed from the planning discussion that preceded this spec.** `fleet-pins.sh`,
  `fleet-gate.sh`, `check-comms-delivery.sh`, and `verify-remotes.sh` were raised as candidates in
  chat before the spec was written, then dropped on closer reading — all four report on OTHER
  projects' health (are consumers pinned, do their gates pass), not on whether dev-platform's own
  code is correct. What made the cut: `check-phase-milestones.sh` and `check-phase-tags.sh` (the
  mechanical backstops for the standard post-merge Roadmap-Phase-completion step) and
  `check-migration-coverage.sh` (an integration test of a tool dev-platform ships, against real
  consumer files) — plus one new check, a genuine fresh `git clone` + `install.sh`/`verify.sh` round
  trip, which catches an untracked-file dependency the existing worktree-based `tests/install/run.sh`
  cannot.

## What shipped

- **`scripts/gate_release.sh`** — runs `gate_fast.sh` in full, then the three fleet-bookkeeping
  checks above (each with 3-way exit-code handling: 0 clean, 1 real problem, 2 setup error, matching
  `check-registry.sh`'s existing pattern in `gate_fast.sh`), then the fresh-clone round trip.
- **`tests/README.md`** — resolved a stale "deferred to a future `gate_full.sh` spec" placeholder to
  point at `gate_release.sh` instead, and clarified that release-tier checks live inline in the
  script itself, not under `tests/` (which stays exclusively `gate_fast.sh`'s offline fixtures).
- **`README.md`** — mentions `gate_release.sh`; also corrected a stale gate-check count (470 → 488,
  re-verified live — the count had drifted since v1.35 without anyone updating this specific mention).

## Two real bugs the adversarial self-review pass caught (not from the spec's own text alone)

1. **A local clone breaks `verify.sh`'s remote-identity check.** `git clone "${REPO}" "${CLONE_DIR}"`
   sets the clone's `origin` to the local path, not `git@github.com:teelr/dev-platform.git` — so
   `verify-remotes.sh` (called by `verify.sh`) always reported a mismatch. Fixed by setting the
   clone's origin to the real expected URL (read from `monitoring/remotes.json`, not hardcoded) right
   after cloning — metadata-only, no network call, stays fully offline.
2. **A second `trap ... EXIT` declaration silently replaces the first, not stacks with it.** The
   spec's own code (written during `/plan`) declared the trap twice — once for `_GATE_COUNTS_FILE`,
   again later repeating that cleanup alongside two new paths. It happened to still work by
   coincidence (the second string repeated the first's job), but reads as if both fire. Consolidated
   into one `_cleanup()` function, registered once.

Neither bug affected the spec's OWN stated expectation for `gate_release.sh`'s exit behavior (both
were caught and fixed before the acceptance test's final real run) — both are documented as lessons:
`tasks/lessons/2026-09-15-local-clone-breaks-remote-identity-verify.md`,
`tasks/lessons/2026-09-15-second-trap-exit-silently-replaces-the-first.md`.
