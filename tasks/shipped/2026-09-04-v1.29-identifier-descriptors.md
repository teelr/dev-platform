# v1.29 Identifier Descriptors — a type word in front of every number

v1.29 Identifier Descriptors, **closes v1.29** (2026-09-04, `tasks/identifier-descriptors-spec.md`): a reader quoted a `/merge` report back and said they could not tell what any of the numbers referred to. They were right, and it was not carelessness — three of the identifiers in it are ambiguous by construction.

The report, from kermit-harness:

> Release cut — `make release VERSION=4.141.0`; tag `v4.141.0` pushed. Milestone **#157** closed — v4.141: Retry Policy Hook. **#383** reply posted, after the Release existed. Left open for Kermit v3 to close, matching how **#365/#366/#367/#369** were handled.

Six numbering systems in three sentences. Decoded against the live repo: `#384` is a **PR**, `#383` is an **issue** — adjacent integers naming different kinds of object, because GitHub gives issues and PRs one shared number space. `milestone #157` holds `v4.141`; the milestone number is a separate sequential counter with no relationship to the version inside it, so citing it communicates nothing a reader can use. And `v4.141` is kermit-harness's Roadmap Phase counter while dev-platform is on `v1.29` and kermit-v3 on `v0.197` — independent counters wearing the same `v<n>.<n>` shape, with nothing in the report saying which project was meant.

## What shipped

**The fix the reader asked for: a descriptor in front of every number.** `issue #383`, `PR #384`, `milestone v4.141: Retry Policy Hook`. Never a bare `#384`. The one exempt form is `owner/repo#N` — the repo name already supplies the context, and GitHub renders it as a cross-repo link.

`CLAUDE.md`'s **Which Identifier To Cite** rule (from v1.26) gains the descriptor mandate stated first, a fourth table row for **milestone numbers** naming real pairs (`milestone #40` holds `v1.29`, `milestone #157` holds `v4.141`), cross-project qualification (`kermit-harness v4.141`, not bare `v4.141`, whenever more than one project is in play), and a before/after of the motivating report.

**The convention now lives in the report templates, which is where it bites.** v1.26's rule governed "prose, reports, commit bodies" in the abstract and no template referenced it — which is why the rule existed for two Roadmap Phases while the offending report still shipped. v1.29 puts it in `settings/claude-global.md`'s required end-of-step format (deployed to `~/.claude/CLAUDE.md`, so it reaches every project's sessions — the motivating report was the harness's, not dev-platform's), and in `commands/merge.md`, `commands/plan.md` and `commands/pr.md`.

**No `gh api` call changed.** The milestone number is the correct API argument; it simply stops appearing in sentences. `commands/merge.md` now says the `<n>` stays in the call and the report says `milestone v<X.Y>: <Title> closed`.

`docs/GLOSSARY.md` gains the two lookups a confused reader actually needs: why a milestone's title and number disagree, and why adjacent `#N` values can be different kinds of object.

## The scope decision: no checker, deliberately

The measurement, taken before deciding rather than after: across `CLAUDE.md`, `commands/`, `docs/` and `settings/` there are **20 `#N` references, 5 without a descriptor — and 4 of those 5 are the exempt `owner/repo#N` form**. The fifth is `Ask #51`, which has one. The tracked markdown was already compliant.

So a file-scanning check would have gone green on its first run and stayed green while chat reports — the surface that actually drifts — went unwatched. That is the vacuous-gate shape this repo already recorded in the v1.25 lesson (a 6-PASS/29-SKIP run that looked like success and proved nothing), and it is exactly what the reader had just complained about elsewhere. Adding one for symmetry with v1.26's `check-phase-tags.sh` would have manufactured the failure. `docs/RULE_RATIONALE.md` records the decision and the numbers so the next phase to touch this does not re-add it.

## The measurement error, kept

The first count said "99 references, 73 with descriptors, ~26 bare." It piped `grep -o` match *fragments* into a second `grep`, so the descriptor test ran against the string `#92` with its line context already stripped, and `-v` filtered fragments rather than lines. The two numbers implied opposite phases — "26 bare" argues for a cleanup pass and a checker; "1 genuinely bare of 20" argues the files were never the problem. A line-context scan settled it. Recorded as `tasks/lessons/2026-09-04-a-count-is-evidence-only-if-the-test-still-sees-context.md`: when a pipeline transforms data between extraction and testing, ask whether the property being tested survived the transform.

Docs-and-rules phase; no scripts, no new tests. Gate at 403 PASS / 0 FAIL / **0 SKIP** — worth noting because v1.14's docs-only-diff skip could have made this run vacuous, and did not: `commands/*.md` deliberately does not count as docs, so the full suite executed.
