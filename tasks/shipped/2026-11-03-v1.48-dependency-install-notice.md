# v1.48 Dependency Install Notice

v1.48 Dependency Install Notice (2026-11-03, `tasks/dependency-install-notice-spec.md`):
fixes issue #151, filed from kermit-v3.

## The problem

In a worktree-mode project every worktree symlinks its `node_modules` back to the main checkout
(`shell/worktree/link-deps.sh`, driven by `.claude/worktree-deps`). A dependency change that
merges to `main` is therefore installed nowhere until someone runs the install in the main
checkout, and nothing in the workflow said so. Per issue #151, on kermit-v3 that went unnoticed
for a week; the install that finally ran replaced Next.js on disk under a running dev server
and every page returned 500 until the server was restarted. (Taken from the issue text; not
re-verified here.)

## What shipped

- `scripts/check-dep-install-needed.sh [commit]` (new, read-only). A `.claude/worktree-deps`
  entry whose last path segment is `node_modules` names a dependency directory; the files
  beside it are `package.json`, `package-lock.json`, `npm-shrinkwrap.json`, `yarn.lock` and
  `pnpm-lock.yaml`. When the commit (default `HEAD`) changed one of them, it prints which
  directory and files, the install command with the MAIN checkout's absolute path, and a line
  to restart the dev server afterwards. The command follows the lock file: npm if
  `package-lock.json` or `npm-shrinkwrap.json` exists, else pnpm, else yarn, else npm.
  It prints nothing otherwise and exits 0 in every case except a usage error (2). It never
  installs, restarts, writes or signals anything.
- `commands/merge.md` Step 6 runs it and relays its output verbatim. Step 7's sub-steps are
  not renumbered.
- `tests/dep-install-notice/run.sh`: 18 checks on fixture git repos, including a parity check
  that runs one manifest through both this script and `link-deps.sh`.
- Docs: `docs/CONCURRENT-DEV.md` ("Dependencies are shared too"), `shell/worktree/README.md`,
  `tests/README.md`.

## Deviation from the spec, and a defect found

The spec had the notice script ignore a trailing `/` on a manifest entry. Running
`link-deps.sh` on `dispatch/node_modules/` showed it does not link such an entry: `ln` fails
(`failed to create symbolic link ... No such file or directory`), yet the script still prints
`linked dispatch/node_modules/` and counts it. Tolerating the slash would have named a
directory that was never linked, so the notice script does not drop it, and the spec was
corrected to match. The `link-deps.sh` defect (an `ln` failure reported as success) is not
fixed here; it is a separate change.

## Scope honesty

- It scans the merge's own commit only. A dependency change that reached `main` another way,
  or a `git pull` that brought in several commits, is not scanned. A check that a lock file is
  newer than `node_modules` (the issue's second ask) was left to each project's own gate.
- Only JavaScript dependency files are detected.
- Whether kermit-pa, keystone or SQRL have drifted the way kermit-v3 did was not checked. Their
  manifests list a `node_modules`, so they now get the notice.
- `SQRL/server` has both `package-lock.json` and `yarn.lock`; the script prints the npm command
  by its lock-file order. Which one SQRL uses there is unverified.
- Not exercised: a real `/merge` on a consumer project with a dependency change. The script is
  tested against fixture repos only. `~/.claude/commands/merge.md` is a symlink to the main
  checkout (`ls -l`), so the new Step 6 text is live at merge.
