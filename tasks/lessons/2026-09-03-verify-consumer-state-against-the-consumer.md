# A claim about another repo's state gets verified against that repo

v1.26 stated that all seven consumer projects pinned `@v0.7` and had therefore never run `check_version_collision.py`. Both halves were wrong. The live pins were `v1.0` through `v1.26`, and three consumers had been running the guard since their `@v1.12`/`@v1.13` bumps. The number came from an example `curl` URL in `docs/CI-INTEGRATION.md:26` that had gone stale years of phases earlier — nobody invented it, it was just read from the nearest thing that looked authoritative and then written into `CLAUDE.md`, `check-phase-tags.sh`, the ROADMAP entry, a lesson file, and the titles of seven issues filed on repos dev-platform does not own.

Two habits would have caught it, and neither is "be more careful." First: `scripts/fleet-pins.sh` was built in v0.8 to answer exactly this question and was never run. A tool existing is not the same as a fact being checked. Second — and this is the sharper one — running it would have answered wrong anyway, because it read each project's **local working copy** rather than the file GitHub Actions runs. OPIE's still differ: local `@v1.12`, live `@v1.2`, because an uncommitted `--force` template overwrite sits in its working tree. So a tool answering is not the same as it answering about the right file. Ask the system that will act on the value: `gh api repos/<slug>/contents/.github/workflows/dev-platform-gate.yml`, not a checkout that may be stale, dirty, or both.

The last part is what makes this expensive rather than embarrassing. A claim about another repo's state is **outbound** the moment it is written down — it went out as seven issue titles telling other maintainers something untrue about their own repos. Corrections have to reach every place the claim landed, not just the file it was written in. When a claim names a repo you do not own, verify it against that repo before it leaves, and if it has already left, count the outbound copies as part of the fix.
