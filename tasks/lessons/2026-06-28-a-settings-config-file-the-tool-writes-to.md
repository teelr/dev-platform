# A settings/config file the tool WRITES to at runtime must never be…

A settings/config file the tool WRITES to at runtime must never be a symlink into a tracked repo — deploy it as a real local file seeded/merged from a tracked baseline. `~/.claude/settings.json` was symlinked to `settings/settings.json`, so every Claude Code "always allow" grant wrote straight through the symlink into the public repo (months of `settings/settings.json` drift, dodged on every commit). The Claude Code docs don't document where grants are written or how to redirect them (claude-code-guide research, all "NOT DOCUMENTED"), so v1.6 fixed it structurally: install.sh now merge-deploys `settings.json` as a real file via `scripts/merge_settings.py` (union the baseline's permission arrays into the live file; baseline wins on config keys), and seeds `settings.local.json` from a secret-free `.example`. Robust regardless of which user file a future Claude writes to, because neither is a repo symlink. Pattern: symlink the read-only artifacts (commands, skills, CLAUDE.md); copy/merge-deploy anything the tool mutates at runtime.
