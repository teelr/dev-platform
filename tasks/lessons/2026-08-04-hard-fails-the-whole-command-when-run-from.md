# `gh pr merge --delete-branch` HARD-FAILS the whole command when run from inside…

`gh pr merge --delete-branch` HARD-FAILS the whole command when run from inside a git worktree — not a benign warning, as `commands/merge.md` incorrectly claimed. Reproduced live on kermit-v3 PR #236: the remote squash-merge succeeded, but `--delete-branch`'s local half needs to check something else out, and `main` is already checked out in the primary checkout (`fatal: 'main' is already used by worktree at '...'`), so the whole `gh pr merge` invocation exits non-zero. `/merge`'s own Step 4 rule ("if `gh pr merge` errors, report verbatim and STOP") then aborted the command right after the remote merge landed but before Step 5's worktree teardown ever ran — leaving the remote branch and worktree both uncleaned, requiring a manual `gh api -X DELETE repos/{owner}/{repo}/git/refs/heads/<branch>` afterward. Fix: Step 4's merge call is now conditional on `IN_WORKTREE` — worktree mode drops `--delete-branch` and deletes the remote branch explicitly via `gh api` (no local checkout touched), leaving local deletion to Step 5's existing `git branch -D`. Bonus catch while fixing this: `gh api`'s endpoint placeholders are `{owner}`/`{repo}`/`{branch}` (curly braces) — the pre-existing `repos/:owner/:repo/milestones/<n>` example at `commands/merge.md`'s Step 6 (colon syntax) is NOT a real gh api placeholder and would 404 if copy-pasted literally; confirmed via `gh api --help` on the installed gh 2.45.0. Left unfixed (out of scope for this spec — it's Step 6 advisory prose, not Step 4/5 code the merge agent executes), flagged here for a future pass. Pattern: a code comment claiming a failure mode is "expected"/"benign" needs the same live-repro verification as any other claim before it's trusted — this one was wrong and silently broke worktree-mode cleanup for every prior `/merge` run since v1.4. SECOND catch, by `/review`: the first cut of the fix used `${BR}` (the worktree's own current branch, from `git branch --show-current`) as the remote-delete target — wrong whenever `/merge <PR_NUM>` merges a PR other than the current branch's own, an explicitly documented supported argument (`commands/merge.md:10`). That combination would delete the wrong (unmerged) remote branch and skip cleanup of the actually-merged one. Fixed by deriving the delete target from `gh pr view "${PR_NUM}" --json headRefName` instead of assuming it equals the caller's own current branch. Pattern: when a fix derives an action's target from "the current session's context" (cwd, current branch, current worktree), check whether the command being fixed supports an explicit-argument override that decouples the target from that context — happy-path testing won't exercise the override, but the code path still ships.
