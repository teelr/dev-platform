# When introducing a new `gh` (or any third-party CLI) invocation, smoke-test against…

When introducing a new `gh` (or any third-party CLI) invocation, smoke-test against the LOCALLY-INSTALLED CLI version before shipping. Don't trust docs that describe flags added in later releases. v0.8's `/merge` slash command spec used `gh pr checks --json name,bucket,state` — that `--json` flag was added in gh ~2.50; local gh is 2.45.0 and rejects it with "unknown flag: --json". Same root cause silently broke the session's earlier Monitor invocations (`gh pr checks N --json name,bucket 2>/dev/null \|\| echo '[]'` swallowed the error and returned `[]` every poll, so PR-CI watchers timed out instead of detecting completion). Fix: switched to `gh pr view <N> --json statusCheckRollup,mergeable,mergeStateStatus` which works on every gh version the workflow supports. Pattern: every new gh subcommand goes through `gh <subcommand> --help` on the LOCAL install first to confirm flag availability — version-skewed docs are a real hazard. Same shape applies to docker, kubectl, jq, awk — when the OS package version may lag the upstream docs by months.
