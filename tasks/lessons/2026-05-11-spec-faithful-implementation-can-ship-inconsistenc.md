# Spec-faithful implementation can ship inconsistencies inherited from the spec itself. v0.5 Phase…

Spec-faithful implementation can ship inconsistencies inherited from the spec itself. v0.5 Phase 3's /review flagged two cross-metric naming/structural inconsistencies (`code_invocations` vs `count`; `events_per_project` inline vs as a metric_* helper) — BOTH of which were literally what the spec prescribed. The fixes were correct (align to `count`; extract the helper), but the deeper lesson is: when /code implements a spec verbatim, /review should still audit for consistency that the spec might have missed. /plan agents are not infallible. Pattern: /review's QUALITY pass looks at the implementation in its full repo context, not just against the spec. Findings that contradict the spec are valid when consistency with the broader codebase wins; flag them as "spec deviation worth absorbing into the next spec revision" rather than treating the spec as immutable.
