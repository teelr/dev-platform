# A count is evidence only if the thing counted still carries what the test needs

Sizing v1.29 meant answering "how many `#N` references in the tracked docs lack a descriptor?" The first attempt piped `grep -o` match *fragments* into a second `grep` that looked for `PR|issue|milestone` before the number. It reported 99 references, 73 with descriptors, ~26 bare. Every part of that was wrong: `-o` prints only the matched text, so the second grep tested the string `#92` with its line context already stripped, and `-v` then filtered fragments rather than lines. A line-context scan gave the real answer — **20 references, 5 without a descriptor, and 4 of those 5 were the already-unambiguous `owner/repo#N` form**.

The two numbers implied opposite phases. "26 bare" says write a cleanup pass and a checker to hold the line. "1 genuinely bare out of 20" says the tracked files were never the problem, the chat reports are, and a file-scanning checker would go green on its first run and stay green while the real surface drifted — the vacuous-gate failure this repo has already recorded. The spec's central scope decision rested entirely on which number was true.

The tell is cheap to look for: **when a pipeline transforms the data between extraction and testing, ask whether the property being tested survived the transform.** `grep -o`, `cut`, `awk '{print $2}'`, `sort -u` all discard context that a downstream filter may need. Prefer a single pass that sees whole lines — a five-line Python scan here — over a clever pipeline whose intermediate form silently drops the thing you are measuring. And when a count is about to decide a phase's shape, spend the extra minute to confirm it by a second, differently-shaped method before writing it into a spec.
