# An issue-reference extractor that includes a bare `#NNN` fallback gives FALSE "delivered"…

An issue-reference extractor that includes a bare `#NNN` fallback gives FALSE "delivered" signals — defeating the checker's purpose. v1.5's `comms_delivery.py` first matched (full URL \| `owner/repo#N` \| `repo#N` \| bare `#N`). The live run marked PA's ollama communique as delivered because it mentions "PR #119" / "PR #121" (PA's OWN PRs) — the bare `#N` matched those, not the harness issue #200 (which the file never links). The whole point is to confirm the communique points at THE upstream repo's issue; a bare `#N` matches any number in any context. Fix: drop the bare-`#N` alternative; require a repo-qualified ref. After the fix both post-cutover PA communiques correctly FAILed (their files link no upstream issue, only the handoff-queue rows do). Pattern: a "does X reference Y" check must require an unambiguous, Y-qualified token — never a fallback loose enough to match unrelated mentions, or every near-miss reads as a hit.
