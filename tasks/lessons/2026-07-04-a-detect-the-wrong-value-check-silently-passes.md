# A "detect the wrong value" check silently passes a MISSING value —…

A "detect the wrong value" check silently passes a MISSING value — a catch-all else branch that means "clean" also swallows "never configured." v1.8's `audit-project-drift.sh` classified chain state as NO_CLAUDE_MD / DRIFT (old chain present) / CLEAN (else) — so a `CLAUDE.md` documenting no workflow chain at all fell through to CLEAN, indistinguishable from a correct chain (SQRL read CLEAN at plan time despite referencing the chain nowhere). Fix: add an explicit positive-presence check (`/code → /review` anchor) BEFORE the else, so absence lands in a distinct MISSING_CHAIN state, not the clean bucket. Pattern: whenever a classifier's "good" state is the fall-through else, ask what an *empty/absent* input yields — if absence reads as good, add a positive-presence gate so "correct" and "never set up" can't collapse into one verdict. Same shape as the v0.9/v1.3 "detector keyed on a bad string" lessons, applied to absence. SECOND catch (surfaced at /code, not /review): a spec's live example can go stale between `/plan` and `/code` when the world changes underneath — SQRL's own session ADDED the canonical chain between the two steps, so the spec's "SQRL flips to MISSING_CHAIN" acceptance criterion became unmeetable (it correctly stayed CLEAN). Verification pivoted to the mock fixture (`no-chain-1`), which is the real regression guard regardless of any one project's current state. Pattern: anchor a change's proof to a controlled fixture, not to a live external project whose state can move between plan and implementation.
