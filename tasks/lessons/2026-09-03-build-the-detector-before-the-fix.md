# Build the detector before the fix, and let it tell you the scope

v1.28's spec ordered Change 9 — the coverage detector — ahead of every parser, on the reasoning that a before-picture proves the phase did something. It paid for itself in a way that ordering did not anticipate: its very first run falsified a claim in the spec that had written it. The survey table said `migrate-shipped.sh` "works" for kermit, because kermit has a `## Recently shipped` section. Nobody had run it. The detector reported `FAILS (aborting, 15 problems)` — kermit's section holds a *table*, not the bullet list the parser expects. A whole parser's worth of scope appeared out of one unverified word, before any code was written against the wrong assumption.

The detector then caught two of its own bugs the same way. It printed `FAILS` rows and exited 0, because `FAILURES` was incremented inside a `probe()` that runs in a command-substitution subshell, where the increment is discarded — a checker that reports failures and passes anyway is worse than no checker. And it reported `PARSES (0 entries)` for four consumers whose files were full of lessons, because a parser that matches nothing exits cleanly; `rc == 0` is not the same as "worked", and a non-empty source yielding zero entries has to count as failure.

Write the check first, run it, and read what it says rather than what you expect it to say. Every number in v1.28's spec that came from a measurement survived; the one that came from an inference ("has the section, therefore works") did not. When a spec asserts a tool's behaviour against input you have not run it on, that sentence is a hypothesis — mark it as one or go run it.
