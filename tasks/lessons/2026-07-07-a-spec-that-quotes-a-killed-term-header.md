# A spec that QUOTES a killed-term header inside a fenced code block…

A spec that QUOTES a killed-term header inside a fenced code block trips `check_spec_taxonomy.sh` on the SPEC FILE itself. v1.10's spec quoted the WORKFLOW_MANUAL.md addition `### Step 7: Post-merge` inside a ```markdown fence; the checker walks every line and does NOT strip code fences, so it matched `^### Step [0-9]+:` under a `## Phase` parent and failed the gate — even though the real WORKFLOW_MANUAL.md file is fine (checker only scans `tasks/*-spec.md` + ROADMAP/planning, and Step-headers are legit for workflow-runner docs). Fix: in the spec, describe such a heading in prose (e.g. "add a `###` subsection titled `Step 7: …`") and put the body in a blockquote — never reproduce a killed-term header at column 0 inside a spec's fence. Pattern: when a spec must show example content containing a killed-term or detector-trigger string, keep that string off column-0 / out of the exact matched form, because the constitutional checkers grep the spec file verbatim. Same family as the recurring "detector self-matches its own documentation" hazard (v0.9/v1.3/v1.8), here applied to a spec quoting the very headers the taxonomy checker bans.
