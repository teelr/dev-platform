# A worktree session's command guard refuses variable-built paths, not outside paths

`/plan` and `/code` both prescribed `bash "${HOME}/.claude/worktree/link-deps.sh" "${MAIN}" "$(pwd)"`, and a worktree-isolated session refuses it with "too complex to verify that it stays inside the worktree" — so the dependency-linking step silently never ran. I first assumed the refusal was about passing the main checkout as an argument, and said so in a PR. It wasn't: `bash /home/rich/.claude/.../link-deps.sh /home/rich/dev .` runs fine, and so does the `~` form with both arguments. Narrowing it took three one-line probes — no args, literal path, tilde — and the trigger is the `${HOME}` expansion alone, because the guard analyses the command statically and cannot resolve a variable.

Write `~/...` in any command a worktree session is expected to run. The guard is also strict about compound commands generally — a heredoc whose *body* contains `git rev-parse`, or a `python3 - <<PY` block followed by a chained check, gets refused too; use one plain command per call, or the Edit/Write tools. And when a guard refuses something, bisect the command rather than believing the first plausible story about which part offended it.
